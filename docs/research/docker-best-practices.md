# Extend Docking Bay's Docker standard past localhost

The project's Docker standard (`docs/standards/docker-and-environment.md`, rules ENV-1 to ENV-15) is a sound **local-development** standard. Its fundamentals match current practice: one multi-stage Dockerfile per workspace built from the repo root, frozen-lockfile installs, no `.env` files in images, committed env templates, NGINX as the single TLS entry point, and mkcert for local certificates. But it stops at the laptop. Compared with late-2026 guidance, it has three kinds of problem. **Five rules rest on outdated or inaccurate assumptions.** These are the full `node:24-bookworm` image as the base for every stage, production included; `corepack enable` just as Node 26, which does not ship Corepack, becomes Active LTS on 28 October 2026; an "aggregate" Compose service where profiles now do the job natively; a MongoDB bind mount that the official image warns against on macOS; and ENV-6's claim that an extending test service "overrides" `env_file`, when Compose actually merges it. **Much more is simply missing.** There is no non-root `USER` and no `.dockerignore`, which ENV-12 depends on. There are no BuildKit cache mounts, no `pnpm deploy`, no image pinning or update automation, no healthchecks and no signal handling. Nothing covers CI, registries, production runtime, production TLS or supply-chain controls. **Events in 2025–26 also raised the baseline:** the Shai-Hulud npm worms, the March 2026 hijack of Trivy's GitHub Actions, Docker Hardened Images going free, and the Docker Content Trust shutdown on 8 December 2026. Almost every fix is cheap: a line or two of Dockerfile, Compose or workflow YAML, free for a public GitHub repo. The recommended path is to keep the existing stage skeleton and dev workflow, correct the five inaccurate rules, and add a production-and-CI half to the standard.

## Dockerfiles keep their five-stage skeleton but need new contents

ENV-9's structure is right and needs no rework. Each workspace has one Dockerfile with named stages `<pkg>-base`, `<pkg>-build`, `<pkg>-dev`, `<pkg>-test` and `<pkg>-prod`, built with the repo root as context. That is the pattern pnpm's own monorepo recipe uses: build everything in one stage, then select each app's final stage with `docker build . --target app1` ([pnpm Docker docs](https://pnpm.io/docker)). The stage names already pass BuildKit's `StageNameCasing` check and map one-to-one onto Bake targets (see the CI section). The problems are in what fills the stages.

**The base image is the main production divergence.** `node:24-bookworm` is a sensible build/dev image because the full Debian image has the toolchain that native addons fall back to. Docker's guidance, though, is to use "two types of base image: one for building and unit testing, and another (typically slimmer) image for production" ([Docker build best practices](https://docs.docker.com/build/building/best-practices/#choose-the-right-base-image)). The `-slim` variant "only contains the minimal packages needed to run node", and Alpine's musl libc "will often run into issues depending on the depth of their libc requirements" ([Docker Hub node](https://hub.docker.com/_/node)). A Debian slim runtime is therefore the safe default for the NestJS backend. Note a detail the standard should spell out: the unqualified `node:24` and `node:24-slim` tags stay on bookworm, while `node:26` and `node:26-slim` already point at **trixie** ([docker-node versions.json](https://github.com/nodejs/docker-node/blob/main/versions.json)). Writing the codename (`24-trixie-slim`) keeps the distro explicit across the coming Node upgrade.

The stronger option is now free. On **17 December 2025 Docker made its Hardened Images catalog free under Apache 2.0**: over 1,000 Debian- and Alpine-based images, each with an SBOM and SLSA Build Level 3 provenance ([Docker press release](https://www.docker.com/press-release/docker-makes-hardened-images-free-open-and-transparent-for-everyone/)). Docker's own Node.js guide now uses them by default, with a `dhi.io/node:24-…-dev` builder and a `dhi.io/node:24-…` runtime ([Docker Node.js guide](https://docs.docker.com/guides/nodejs/)). The runtime images run as non-root and have **no shell and no package manager** ([DHI migration checklist](https://docs.docker.com/dhi/migration/checklist/)). That rules out `pnpm` and `curl` in production and requires a free `docker login dhi.io` in every build environment. Two details remain unresolved. The exact Debian-flavour tag names could not be confirmed. And Docker's documents disagree on the runtime user: the generic checklist says UID 65532 `nonroot`, while the Node migration example uses `node:node` ([DHI Node migration example](https://docs.docker.com/dhi/migration/examples/node/)). Recommendation: make `node:24-trixie-slim` the minimum for `-prod`, and treat a Debian-flavoured DHI runtime as the hardened upgrade.

**Pinning is absent from the standard.** Tags are mutable. Docker recommends pinning to a digest and letting Dependabot's `docker` ecosystem raise PRs that bump "tags and digests". It calls that "better than using a tag that changes the version automatically" ([Docker build best practices](https://docs.docker.com/build/building/best-practices/#pin-base-image-versions)). Renovate's `config:best-practices` includes `docker:pinDigests` ([Renovate Docker docs](https://docs.renovatebot.com/docker/#digest-pinning)). One caveat should go into the rule itself: a digest pin without an updater is worse than a floating tag, because security fixes silently stop arriving. Pinning also guards against a concrete hazard: the `lts` tag moves from 24 to 26 on 28 October.

**Dependency installation is the biggest build-speed gap.** ENV-10's bare `RUN pnpm install --frozen-lockfile` has no cache mount, so any source change that invalidates the layer re-downloads every package. pnpm's current recipe installs with `RUN --mount=type=cache,id=pnpm,target=…` over the store, builds, then runs `pnpm deploy --filter=<app> --prod <dir>` and copies only that directory into the runtime stage ([pnpm Docker docs](https://pnpm.io/docker)). Ephemeral CI runners may not keep cache mounts. There, `pnpm fetch`, which reads only the lockfile and `pnpm-workspace.yaml`, followed by `pnpm install --offline`, yields a dependency layer that "will only be lost when you change the dependencies" and avoids copying every workspace `package.json` ([pnpm fetch](https://pnpm.io/cli/fetch)). pnpm also warns that omitting `pnpm-workspace.yaml` from the pre-install copy "can change how dependencies are installed or make a frozen install fail". It warns that a warm store baked into an image layer silently turns hard links into copies, and that a store cache must be shared only between mutually trusted builds ([pnpm Docker docs](https://pnpm.io/docker)).

`pnpm deploy` is how ENV-12's promise that production stages hold "only built output and production dependencies" gets met, but its behaviour depends on the pnpm major. On pnpm 10 it needs `injectWorkspacePackages: true` or `--legacy` ([pnpm 10 deploy](https://pnpm.io/10.x/cli/deploy)). From **pnpm 11.26.0 and 12.2.0** it rewrites workspace links to `file:` dependencies and no longer needs injection ([pnpm 11 deploy](https://pnpm.io/11.x/cli/deploy); [pnpm 12 deploy](https://pnpm.io/cli/deploy)). Deploy copies files according to the package's `files` field, falling back to `.npmignore` and then `.gitignore` ([pnpm deploy](https://pnpm.io/cli/deploy)). The deploy docs don't spell out the consequence for this repo, but it follows from that rule: `backend` and `shared` should both declare `"files": ["dist"]`, or a git-ignored `dist/` may be left out of the deployed bundle.

**Corepack has a hard end date for this project.** Node 24 still bundles Corepack (0.36.0 in v24.21.0), but **Node 25 stopped distributing it** in a semver-major change ([Node.js v25 changelog](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V25.md)). Node 24's own docs say users "can switch to using the userland-provided corepack module" ([Node.js v24 Corepack docs](https://nodejs.org/docs/latest-v24.x/api/corepack.html)). pnpm's documentation has moved on as well. Its CI page notes that Corepack's shim starts Node before every pnpm call and recommends installing pnpm directly. pnpm then switches to the `packageManager` version on first use, "so the pipeline does not pin a version in two places" ([pnpm CI docs](https://pnpm.io/continuous-integration)). The 11.x and 12.x Docker recipes use `ghcr.io/pnpm/pnpm` with no Corepack, and pnpm 12 is a native executable ([pnpm installation](https://pnpm.io/installation)). Node 24 enters maintenance on 20 October 2026, and Node 26 becomes Active LTS on 28 October ([docker-node versions.json](https://github.com/nodejs/docker-node/blob/main/versions.json)). A sibling rule (NODE-1, "use the active LTS line") will therefore soon point at a Node line without Corepack. `corepack enable` is acceptable for as long as the repo stays on Node 24. The standard should already name the successor: the standalone pnpm binary pinned to `packageManager`, or a `ghcr.io/pnpm/pnpm` build stage. `npm install -g corepack` would break NODE-2's "no npm in Dockerfiles" rule, and `COREPACK_INTEGRITY_KEYS=0` disables signature checks; neither is acceptable.

**Runtime identity and signals are unspecified.** The `node` images ship a `node` user with UID 1000, and docker-node's best practices say to switch to it because root "violates the Principle of Least Privilege" ([docker-node best practices](https://github.com/nodejs/docker-node/blob/main/docs/BestPractices.md#non-root-user)). The standard never mentions `USER`. For signals, "Node.js was not designed to run as PID 1": it will not respond to SIGINT and similar signals unless an init such as tini wraps it ([docker-node best practices](https://github.com/nodejs/docker-node/blob/main/docs/BestPractices.md#handling-kernel-signals)). The same guide says to bypass `npm start` and run `node` directly so SIGTERM reaches the app. ENV-11's `ENTRYPOINT ["pnpm", "backend:base"]` is fine for dev and test, where `docker compose run backend <script>` flexibility is worth a slow Ctrl-C. Production, though, needs exec-form `CMD ["node", "dist/main.js"]` plus Compose's `init: true`, which "runs an init process (PID 1) inside the container that forwards signals and reaps processes" ([Compose services reference](https://docs.docker.com/reference/compose-file/services/#init)). On the app side, NestJS runs its shutdown hooks on SIGTERM only after `app.enableShutdownHooks()` is called ([NestJS lifecycle events](https://docs.nestjs.com/fundamentals/lifecycle-events#application-shutdown)). Without that, Mongo and WebSocket connections are not closed cleanly. No pnpm documentation describes whether `pnpm run`, now a native binary in v12, forwards signals, so "never run pnpm as the production process" should stay a firm rule.

**Two cheap authoring guardrails are missing.** A `# syntax=docker/dockerfile:1` first line makes every builder use the same, current Dockerfile frontend ([Dockerfile reference](https://docs.docker.com/reference/dockerfile/#syntax)). `# check=error=true` turns BuildKit's built-in checks into build failures ([Docker build checks](https://docs.docker.com/build/checks/)). Those checks include `SecretsUsedInArgOrEnv`, `JSONArgsRecommended`, `WorkdirRelativePath` and `CopyIgnoredFile` ([build checks reference](https://docs.docker.com/reference/build-checks/)). hadolint, still maintained (v2.15.1, July 2026), adds ShellCheck coverage of `RUN` lines ([hadolint releases](https://github.com/hadolint/hadolint/releases)).

Finally, ENV-12's "never copy `.env` files into an image" is enforceable only with a root `.dockerignore`, and the standard has none. Because ENV-9 makes the whole repo the build context, a missing ignore file also uploads `.docker/` (local Mongo data, ENV-8) and `certs/` (mkcert keys, ENV-14) on every build. Docker's and pnpm's examples agree on excluding `node_modules`, `dist`, `.git` and `.env` ([Docker Node.js guide](https://docs.docker.com/guides/nodejs/); [pnpm Docker docs](https://pnpm.io/docker)). This repo should add `**/` prefixes plus `.docker/`, `certs/`, coverage and logs. For the frontend, Docker's React guide serves the Vite `dist/` from **`nginxinc/nginx-unprivileged`** on port 8080 as user `nginx`, "to follow security best practices" ([Docker React.js guide](https://docs.docker.com/guides/reactjs/)). A `frontend-prod` stage on that image keeps ENV-13's role-named `frontend` upstream unchanged between dev and prod.

The backend Dockerfile below keeps ENV-9's stage names. It assumes packages named `@app/*` and pnpm ≥ 11.26 or ≥ 12.2. It is a starting point to adapt, not a tested file:

```dockerfile
# syntax=docker/dockerfile:1
# check=error=true
# Renovate/Dependabot keep tag + digest current
ARG NODE_BUILD=node:24.21.0-trixie@sha256:<digest>
ARG NODE_RUNTIME=node:24.21.0-trixie-slim@sha256:<digest>

FROM ${NODE_BUILD} AS backend-base
ENV PNPM_HOME=/pnpm PATH=/pnpm:$PATH COREPACK_ENABLE_DOWNLOAD_PROMPT=0
# Node 24 only; replace with the standalone pnpm binary on Node 26
RUN corepack enable
WORKDIR /repo
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
RUN --mount=type=cache,id=pnpm,target=/pnpm/store pnpm fetch
COPY . .
RUN --mount=type=cache,id=pnpm,target=/pnpm/store pnpm install --frozen-lockfile --offline

FROM backend-base AS backend-build
# "..." = backend plus its workspace deps, so shared builds first
RUN pnpm --filter "@app/backend..." build
RUN pnpm --filter @app/backend --prod deploy /out

FROM backend-base AS backend-dev
ENTRYPOINT ["pnpm", "backend:base"]
CMD ["start:dev"]

FROM ${NODE_RUNTIME} AS backend-prod
ENV NODE_ENV=production
WORKDIR /app
# root-owned, read-only app files; the process runs unprivileged
COPY --link --from=backend-build /out ./
USER node
EXPOSE 3000 8080
CMD ["node", "dist/main.js"]
```

The `--filter "@app/backend..."` selector replaces ENV-10's two hard-coded build lines. It builds `shared` first in dependency order, which matches the monorepo standard's own idiom. `NODE_ENV=production` stays out of the install stages so devDependencies are still available for the build.

## Compose for dev: three rules are inaccurate and health handling is missing

The dev Compose rules mostly hold up. Committed templates, placeholder secrets and isolated test config (ENV-1 to ENV-4) agree with Docker's advice to "use different `.env` files as needed" per environment ([Docker env var best practices](https://docs.docker.com/compose/how-tos/environment-variables/best-practices/)). Routing everything through the proxy instead of hard-coding `localhost` (ENV-15) is right. So is mkcert behind NGINX (ENV-14). Caddy's internal CA might look simpler, but its own docs say installing the root into trust stores "isn't guaranteed to work, especially if containers are being used" ([Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https)), so moving off mkcert gains little locally. Three rules need correcting, though, and several gaps need filling.

**ENV-6 misdescribes `extends`.** Under `extends`, `env_file` and `volumes` are **merged**, child on top of parent, and `depends_on` is **not copied at all** ([Compose services reference](https://docs.docker.com/reference/compose-file/services/)). A `backend-test` service that "overrides `env_file`" therefore loads `.env` *and* `.env.test`, which works only if `.env.test` redefines every conflicting key. It must also redeclare its own `depends_on`. ENV-6's blanket "`env_file`, not inline `environment`" is also stricter than Docker's model. Compose resolves variables in this order: `run -e`, then interpolated `environment`/`env_file` values, then literal `environment`, then `env_file`, then Dockerfile `ENV`. The project-root `.env` drives **interpolation of the Compose file itself**; it does not set container environment ([Compose env precedence](https://docs.docker.com/compose/how-tos/environment-variables/envvars-precedence/)). A more accurate rule loads app config through `env_file` and allows `environment` for three things: interpolated derived values such as a Mongo URI, fixed per-service constants, and `*_FILE` secret pointers. It should forbid duplicate keys across the two. The standard should also state the dual role of `.env` outright, because the confusion is real: `${BACKEND_PORT}` in `ports:` comes from `.env` or the shell, while the container sees only what `env_file` passes in.

**ENV-5's aggregate service duplicates a native feature.** "Services without a `profiles` attribute are always enabled", and naming a profiled service on the command line activates its profile automatically ([Compose profiles](https://docs.docker.com/compose/how-tos/profiles/)). Leaving `mongo`, `backend`, `frontend` and `proxy` unprofiled makes `docker compose up` start the stack. Putting `backend-test` under `profiles: [test]` means `docker compose run --rm backend-test` just works. No dummy container is left showing up in `docker compose ps`.

**ENV-8's Mongo bind mount contradicts the image maintainers.** The official `mongo` image warns that on macOS and Windows "the file systems used to share between the host system and the Docker container is not compatible with the memory mapped files used by MongoDB" and directs Docker Desktop users to named volumes ([Docker Hub mongo](https://hub.docker.com/_/mongo)). Current VirtioFS file sharing may tolerate it, but the warning still stands. A named `mongo-data` volume also avoids host UID problems and gives `docker compose down -v` a clean reset. `.docker/` can stay for git-ignored secrets and seed files.

Test isolation (ENV-4) works today through different DB names and ports. A separate project is the stronger mechanism: `docker compose -p msg-docking-bay-test --env-file .env.test --profile test run --rm backend-test`. It gets its own containers, network and named volumes, so tests can never touch dev data, and `--env-file` swaps the interpolation file. This follows directly from the profile and precedence docs above, though no single Docker page prescribes it.

**Startup ordering is entirely missing.** "Compose does not wait until a container is 'ready', only until it's running." Docker's documented fix is a `healthcheck` on the dependency plus `depends_on: { condition: service_healthy, restart: true }`. The `restart: true` part reconnects dependants when Mongo restarts ([Compose startup order](https://docs.docker.com/compose/how-tos/startup-order/)). The proxy needs this too: NGINX resolves `upstream` hostnames at startup, so starting before `backend` exists makes it fail. A `mongosh --eval "db.adminCommand('ping').ok"` check is the common Mongo probe ([OneUptime, 2026](https://oneuptime.com/blog/post/2026-03-31-mongodb-docker-health-checks/view)). The Node services can use a `node -e "fetch(…)"` one-liner, because slim and hardened images lack `curl`.

**Publishing ports is a quiet security gap.** Docker's own docs state that "publishing container ports is insecure by default" because ports bind to all interfaces; `127.0.0.1:` prefixes keep them local ([Docker port publishing](https://docs.docker.com/engine/network/port-publishing/)). Only the proxy needs published ports, on loopback. Mongo should publish none, or `127.0.0.1:${DB_PORT}:27017` if a developer wants Compass. ENV-13 implies this but doesn't require it.

**ENV-7's bind-mount workflow is still acceptable, and Compose Watch is now Docker's lead pattern.** Docker's React and Node guides use `develop.watch`, with `sync` for source and `rebuild` for `package.json`. They warn against syncing `node_modules`, and Docker describes Watch as complementing bind mounts rather than replacing them ([Use Compose Watch](https://docs.docker.com/compose/how-tos/file-watch/)). In a pnpm monorepo the bind-mount pattern has specific traps. Anonymous `node_modules` volumes keep stale dependencies after lockfile changes (`up -V` renews them), and root plus each workspace has its own `node_modules` to mask. Watch writes files into the container's own filesystem, so native file watching works without polling. If the standard keeps bind mounts, it should document `-V`. If backend reload fails under bind mounts, adjust TypeScript's `watchOptions`, which governs `nest start --watch`'s default tsc compiler ([TypeScript watch config](https://www.typescriptlang.org/docs/handbook/configuring-watch.html)). The often-copied `CHOKIDAR_USEPOLLING` variable affects Vite and webpack watchers, not tsc.

**The Vite-behind-NGINX details are missing, and they break HMR when absent.** Vite needs `server.host: true`, `strictPort: true` and an explicit `allowedHosts` that includes `APP_DOMAIN`. Vite warns that `allowedHosts: true` "allows any website to send requests to your dev server and download your source code" ([Vite server options](https://vite.dev/config/server-options)). NGINX must set the hop-by-hop `Upgrade` and `Connection` headers explicitly through the `map $http_upgrade $connection_upgrade` idiom. It closes connections idle for 60 seconds by default ([nginx WebSocket proxying](https://nginx.org/en/docs/http/websocket.html)). Those headers belong on the `/` location as well as the WebSocket location, because Vite's HMR socket uses the frontend route, which is a common oversight. Node containers that call the proxy over HTTPS, such as e2e runners, also need `NODE_EXTRA_CA_CERTS` pointing at a mounted mkcert root certificate, never the root key.

Smaller items round this out. Compose is now on **v5.x** (v5.6.0, 2 October 2026), and the top-level `version:` key is obsolete and only emits a warning ([docker/compose releases](https://github.com/docker/compose/releases); [Compose version and name](https://docs.docker.com/reference/compose-file/version-and-name/)). The standard should require `name: msg-docking-bay`, forbid `version:` and prefer the canonical `compose.yaml` filename. Compose v5 builds through Bake, so contributors on Podman or Colima need buildx installed. `init: true` on the pnpm-fronted dev services makes `docker compose stop` fast. `pull_policy` refresh windows such as `daily`, added in Compose v5.2, keep pinned `mongo:8` and `nginx` tags patched without pulling on every `up` ([docker/compose releases](https://github.com/docker/compose/releases)).

```yaml
name: msg-docking-bay
services:
  mongo:
    image: mongo:8
    volumes: [mongo-data:/data/db]
    healthcheck:
      test: ["CMD", "mongosh", "--quiet", "--eval", "db.adminCommand('ping').ok"]
      interval: 10s
      retries: 5
      start_period: 30s
  backend:
    build: { context: ., dockerfile: backend/Dockerfile, target: backend-dev }
    env_file: [.env]
    init: true
    depends_on: { mongo: { condition: service_healthy, restart: true } }
  backend-test:
    extends: { service: backend }
    profiles: [test]
    build: { target: backend-test }
    env_file: [.env.test]   # merged on top of .env, not a replacement
    depends_on: { mongo: { condition: service_healthy } }   # not inherited
  proxy:
    ports: ["127.0.0.1:443:443", "127.0.0.1:80:80"]
volumes:
  mongo-data:
```

## Supply-chain incidents in 2025–26 made several "nice-to-haves" mandatory

The standard's only security rules are "no committed secrets" and "no `.env` in images". Between September 2025 and March 2026 the threat model moved. **Shai-Hulud**, a self-propagating npm worm, compromised more than 500 packages in September 2025. It stole GitHub tokens and cloud keys through install-time code and republished itself into more packages. CISA's response recommended lockfile audits, credential rotation, phishing-resistant MFA and Dependabot ([CISA alert](https://www.cisa.gov/news-events/alerts/2025/09/23/widespread-supply-chain-compromise-impacting-npm-ecosystem)). pnpm answered with defaults that now belong in the standard. v10 stopped running dependency lifecycle scripts by default. **pnpm 11 (28 April 2026) set `minimumReleaseAge` to 1,440 minutes, turned on `blockExoticSubdeps` and `strictDepBuilds`, and collapsed the old build allow/deny settings into one `allowBuilds` map** ([pnpm 11.0 release notes](https://pnpm.io/blog/releases/11.0)). `trustPolicy: no-downgrade` additionally refuses a release whose trust level, such as trusted publishing, drops below earlier versions ([pnpm supply-chain security](https://pnpm.io/supply-chain-security)). With `strictDepBuilds`, a Docker build fails when a new transitive dependency suddenly wants to run a postinstall script, which is exactly the Shai-Hulud vector. The setting names differ between pnpm 10 (`onlyBuiltDependencies`) and pnpm 11+ (`allowBuilds`), so the standard has to state which pnpm major the repo targets before it can codify them.

The second shock hit the CI layer. Between **19 and 23 March 2026**, attackers force-pushed 76 of 77 `aquasecurity/trivy-action` tags, and every `setup-trivy` tag, to an infostealer that harvested CI secrets. They also shipped malicious Trivy binaries and images ([Trivy advisory GHSA-69fq-xp46-6x23](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23); [Microsoft Security blog](https://www.microsoft.com/en-us/security/blog/2026/03/24/detecting-investigating-defending-against-trivy-supply-chain-compromise/)). Anyone referencing a floating tag ran the attacker's code. The lesson applies to every action, not just scanners: **pin every third-party GitHub Action to a full commit SHA**, give each job minimal `permissions`, and keep secrets out of jobs that run `pnpm install` or `docker build`.

At build time, Docker is categorical that ARG and ENV "are inappropriate for passing secrets because they persist in the final image". The replacement is `RUN --mount=type=secret` ([Docker build secrets](https://docs.docker.com/build/building/secrets/)). There is a GitHub-specific twist. `docker/build-push-action` attaches `mode=max` provenance to images from public repos automatically, and that provenance "contains the values of build arguments" ([Docker attestations with GitHub Actions](https://docs.docker.com/build/ci/github-actions/attestations/)). A secret passed as an ARG in this public repo would therefore be published. Today the repo uses only public packages, so the forward-looking rule is: any registry token reaches `pnpm install` only through a secret mount scoped to that one `RUN`.

At runtime, OWASP's Docker cheat sheet lists the same short set of controls as before. Never expose the Docker socket ("equivalent to giving unrestricted root access to your host"). Set a non-root user, drop all capabilities, and run with `no-new-privileges`. Limit resources, and use a read-only root filesystem ([OWASP Docker Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html)). In Compose each of these is one line. Node and Mongo need no extra capabilities on ports above 1024. NGINX needs none on the unprivileged image, which listens on 8080 and moves its PID and temp paths to `/tmp`; that makes `read_only: true` plus a `/tmp` tmpfs workable ([nginx-unprivileged](https://github.com/nginx/docker-nginx-unprivileged)). For MongoDB, the official image runs **with no authentication unless both `MONGO_INITDB_ROOT_USERNAME` and `MONGO_INITDB_ROOT_PASSWORD` are set**, and those two variables accept `_FILE` variants for Docker secrets ([Docker Hub mongo](https://hub.docker.com/_/mongo)). Docker recommends Compose `secrets:` mounted at `/run/secrets/` over environment variables. Environment variables are "often available to all processes" and "can also be printed in logs when debugging errors without your knowledge" ([Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/)).

On provenance and signing, **Docker Content Trust shuts down entirely on 8 December 2026**, after brownouts in July and August. Docker's migration guidance recommends digest pinning, Sigstore/cosign or Notation, and Hardened Images as the "free alternative with cryptographic signatures built-in" ([Docker DCT retirement guidance](https://www.docker.com/blog/docker-content-trust-retirement-and-migration-guidance/)). GitHub artifact attestations are free for public repositories ([GitHub artifact attestations](https://docs.github.com/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-to-establish-provenance-for-builds)). For scanning, OWASP lists Trivy, Grype and Clair as free and Docker Scout as freemium ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html)). No authoritative 2026 head-to-head comparison exists. For a project this size, how the scanner is wired in matters more than which one it is: SHA-pinned, failing only on fixable HIGH/CRITICAL findings, and run weekly on a schedule, because new CVEs appear without code changes.

|---|---|---|
| Non-root `USER`, slim/hardened prod base, no Docker socket, no `privileged` | Must | OWASP core rules; zero cost |
| Version-pinned tags; digests plus Dependabot/Renovate | Must (tags) / Should (digests) | Docker pinning guidance; DCT retirement |
| All GitHub Actions pinned by commit SHA; minimal job permissions | Must | Trivy action hijack, March 2026 |
| No secrets in ARG/ENV/COPY; `# check=error=true` | Must | Build secrets docs; public-repo provenance leaks ARGs |
| pnpm frozen lockfile + `allowBuilds`/`strictDepBuilds` | Must | Shai-Hulud; pnpm 11 defaults |
| `minimumReleaseAge`, `blockExoticSubdeps`, `trustPolicy: no-downgrade` | Should | pnpm supply-chain docs |
| Mongo auth via `_FILE` secrets, least-privilege app user, no public 27017 | Must in prod | mongo image docs; OWASP 5a |
| `cap_drop: [ALL]`, `no-new-privileges`, `read_only` + tmpfs, resource limits | Must/Should in prod; optional in dev | OWASP rules 3, 4, 7, 8 |
| CI image scan, fail on fixable HIGH/CRITICAL | Should | OWASP rule 9 |
| SBOM + provenance on pushed images | Should, once pushing | Two lines in build-push-action |
| cosign or attestation verification, admission policy | Skip until there is a deploy pipeline | Enterprise-grade |

## CI and production are undefined, and the 2026 defaults make them easy

The standard defines no build pipeline, registry, tagging scheme, production Compose file, production TLS or production database, so these are additions rather than corrections. Several 2025–26 changes make them easier.

**Bake is the natural build front end for this monorepo.** `docker buildx bake` went GA on 5 February 2025. Docker names "monorepos & image bakeries" as a primary use case and lists parallel builds and **deduplicated context transfers** when targets share a context ([Docker Bake GA](https://www.docker.com/blog/ga-launch-docker-bake/)). Every image here shares the repo-root context, so one `docker-bake.hcl` can declare `backend-prod`, `frontend-prod` and a `backend-test` target with `output = ["type=cacheonly"]` ([Docker Bake guide](https://docs.docker.com/guides/bake/)), with no Dockerfile changes. The current official actions are `setup-buildx-action@v4`, `build-push-action@v7`, `login-action@v4` and `setup-qemu-action@v4` ([Docker multi-platform CI docs](https://docs.docker.com/build/ci/github-actions/multi-platform/)), plus `metadata-action@v6` ([metadata-action](https://github.com/docker/metadata-action)). Blog posts showing v5/v6 or v3 are out of date. The recommended cache is `type=gha` with `mode=max`. The legacy GHA cache API was retired on 15 April 2025, which raised the floor to **Buildx 0.21, BuildKit 0.20 and Compose 2.33.1**. The GHA cache is read-only for `pull_request_target` and similar events ([Docker GHA cache docs](https://docs.docker.com/build/ci/github-actions/cache/)). With two or more images, give each its own cache `scope` so one image's `mode=max` export doesn't evict the other's. Check the exact parameter on the [gha backend page](https://docs.docker.com/build/cache/backends/gha/) before codifying it.

The test flow Docker documents is to build with `load: true`, run the tests, then push. The push reuses the cache, so "the `linux/amd64` image is only built once" ([Docker test-before-push](https://docs.docker.com/build/ci/github-actions/test-before-push/)). For this repo that suggests three jobs. The first runs frontend and shared unit tests directly on the runner for speed. The second runs backend integration tests through the existing `backend-test` Compose service against a real Mongo, so CI and local dev take the same path the testing standard already prescribes. The third builds and pushes only on `main` and `v*` tags, after both test jobs pass.

**Multi-arch is free to do properly.** GitHub's arm64 hosted runners (`ubuntu-24.04-arm`) went GA on 7 August 2025 and are **free for public repositories** ([GitHub changelog](https://github.blog/changelog/2025-08-07-arm64-hosted-runners-for-public-repositories-are-now-generally-available/)). Docker's `docker/github-builder` reusable workflow sends ARM platforms to those runners automatically. Docker warns that building several platforms on one runner "can significantly extend build times" ([Docker multi-platform CI docs](https://docs.docker.com/build/ci/github-actions/multi-platform/)). Whether multi-arch matters depends on the deploy host: arm64 VPS plans are common and cheap, and developers on Apple Silicon reproduce bugs locally. The rule the standard needs regardless is that **production images are built only in CI**. A laptop push from a Mac produces an arm64-only image that fails on an amd64 server.

**GHCR is the obvious registry, and deploys should reference immutable tags.** GHCR authenticates with `GITHUB_TOKEN` and `packages: write`. The `org.opencontainers.image.source` label links an image to its repo ([GitHub Container registry docs](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)), and `metadata-action` emits it and other OCI labels automatically. Its `type=sha`, `type=semver` and `type=raw,value=latest,enable={{is_default_branch}}` tag set ([metadata-action](https://github.com/docker/metadata-action)) gives each main build a `sha-<7>` tag and each release `X.Y.Z` and `X.Y` tags. Deploys should pin a `sha-` tag or digest so rollback means redeploying the previous one; `latest` should never appear in deploy config. The Conventional Commits rules in the git standard already supply what release-please or semantic-release need to cut those version tags. Docker Hub still matters, because base images come from there. Its unauthenticated limit remains **100 pulls per 6 hours per IP**, and 200 for a free authenticated account ([Docker Hub pull limits](https://docs.docker.com/docker-hub/usage/pulls/)). Docker cancelled its planned April 2025 tightening ([Docker blog](https://www.docker.com/blog/revisiting-docker-hub-policies-prioritizing-developer-experience/)). Logging CI into Docker Hub with a free token doubles that limit and stops runners competing for a shared IP's quota.

**Production on a single VPS is officially a Compose job.** Docker's docs endorse a `compose.production.yaml` override that removes code bind mounts, changes port bindings and sets a restart policy ([Use Compose in production](https://docs.docker.com/compose/how-tos/production/)). Two defaults bite here. The `json-file` log driver "does not perform log-rotation by default", and Docker recommends the `local` driver, which rotates ([Docker logging drivers](https://docs.docker.com/engine/logging/configure/)). The default `max-size` is unlimited ([json-file driver](https://docs.docker.com/engine/logging/drivers/json-file/)). A widely shared 2026 Compose tip calls `10m`/`3` the json-file "defaults" ([lours.me](https://lours.me/posts/compose-tip-033-logging-drivers/)). That contradicts Docker's documentation: those are recommended settings that must be set explicitly. Containers also get **10 seconds** between SIGTERM and SIGKILL. A WebSocket gateway that drains connections needs a longer `stop_grace_period`, with the app's internal shutdown timeout set just below it ([lours.me Compose tip #18](https://lours.me/posts/compose-tip-018-graceful-shutdown/)). The 12-factor model (config from the environment, logs as unbuffered stdout) is already in the standard ([Twelve-Factor config](https://12factor.net/config); [logs](https://12factor.net/logs)). ENV-12 should say "Compose `env_file` *or* platform secrets" so a later move to a PaaS doesn't break the rule. The logging standard's human-readable `loglevel` output satisfies stdout but parses poorly once shipped elsewhere. If log aggregation is ever planned, JSON lines in production is worth a cross-standard decision.

Zero-downtime deploys are where WebSockets cost something. The `docker rollout` plugin can replace a Compose service behind a proxy once the new container passes its healthcheck. It requires no `ports` and no `container_name` on the service, and it names Traefik and nginx-proxy as the supported proxies ([docker-rollout](https://github.com/wowu/docker-rollout)). Open WebSocket connections die when the old container stops regardless. The pragmatic target for this app is a one-to-two-second reconnect. The server sends a close frame on SIGTERM, and the client reconnects with jittered backoff and re-fetches full state. NGINX's `proxy_read_timeout` **defaults to 60 seconds** and closes idle WebSockets ([nginx proxy module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout)), so server pings must arrive faster than that, or the timeout must be raised. One open question belongs in the standard: ENV-13 names a separate `websocket` upstream, which makes sense only if the gateway runs as its own process rather than on `WS_PORT` inside the Nest app.

**Production TLS and the production database are deploy-target decisions the standard should frame.** ENV-14 covers only local mkcert. Caddy issues and renews Let's Encrypt certificates and redirects HTTP to HTTPS by default, needing only ports 80/443 and a persistent data directory ([Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https)). That is the lowest-maintenance edge for one VPS. Keeping NGINX for parity with local dev is equally valid if a certbot container plus a reload job handles renewal. NGINX's HTTP/3 is still experimental and absent from default builds ([nginx HTTP/3 module](https://nginx.org/en/docs/http/ngx_http_v3_module.html)), so it should not be a requirement. On a PaaS, the platform terminates TLS and the NGINX TLS block becomes dev-only. For MongoDB, Atlas M0 is explicitly not for production: 0.5 GB, 100 ops/s and "backups are not supported" ([Atlas free limits](https://www.mongodb.com/docs/atlas/reference/free-shared-limitations/)). Atlas Flex offers 5 GB, 500 ops/s and **one automatic daily snapshot with no point-in-time recovery** ([Atlas Flex limitations](https://www.mongodb.com/docs/atlas/reference/flex-limitations/)), which means up to 24 hours of data loss in the worst case. That is likely acceptable for favourites and accounts, but the standard should state it as the recovery point objective. Self-hosting Mongo in the prod Compose stack is acceptable only with auth, no published port, a named volume, and scripted off-host `mongodump` backups that have actually been test-restored. ENV-3's `DB_HOST`/`DB_PORT` split cannot express Atlas's `mongodb+srv://` strings, so a `DB_URI` variable is needed either way.

Finally, the standard should name version floors. **Docker Engine 29** (11 November 2025) raised the minimum API version to 1.44 and made the containerd image store the default for new installs ([Docker Engine v29](https://www.docker.com/blog/docker-engine-version-29/)). Compose v5.3 added native init containers and v5.6 manual jobs, which give migrations and seed steps a first-class home ([docker/compose releases](https://github.com/docker/compose/releases)). A floor of "Engine ≥ 29, Compose v5.x (≥ 2.33.1 absolute minimum), Buildx ≥ 0.21" covers every feature recommended here.

## Conclusion

The pattern behind these findings is that the standard was written to describe a working dev setup, while current Docker practice is mostly about what happens after `docker compose up` succeeds: who the process runs as, what it was built from, how it was verified, and how it stops. The largest risks for this project are not exotic. They are the defaults the standard leaves in place: a root process in a full Debian image, floating tags on images and actions, unrotated logs, a 10-second kill window in front of WebSocket clients, and an unauthenticated Mongo. Each of these is fixed with configuration, not architecture. The one time-sensitive item is the Node 26 transition. Within weeks, NODE-1 will point at an LTS line without Corepack, and the base-image tags will silently switch distro, so the pnpm-installation rule and image pinning should land before that upgrade, not during it.

Several facts were not settled by the sources and should be verified before they become rules: DHI's Debian Node tag names and runtime UID, whether pnpm 12's native `pnpm run` forwards signals, the GHA cache `scope` parameter, whether the `mongo` image tolerates `read_only: true`, and which pnpm major the repo actually targets, since the supply-chain setting names depend on it. None of these unknowns changes the direction. Splitting the document into a dev half that stays largely intact and a new production, CI and security half is the smallest change that brings Docking Bay's standard in line with 2026 practice.
