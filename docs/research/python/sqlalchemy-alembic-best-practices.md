# Type the models, then review every migration

As of 5 October 2026, best practice for SQLAlchemy and Alembic on PostgreSQL has four parts. First, **target SQLAlchemy 2.1** (2.1.3, released 2 October 2026), **Alembic 1.20** and **psycopg 3 through an explicit `postgresql+psycopg://` URL**. The 2.0 line (2.0.54) stays supported but the docs now label it "legacy". Second, **declare every model with `DeclarativeBase`, `Mapped[...]` and `mapped_column()`, and centralise PostgreSQL types in a `type_annotation_map` and `Annotated` aliases.** That gives pyright strict full attribute, query and result typing with no plugin. The mypy plugin is gone in 2.1. Third, keep the `Session` lifecycle in the caller, with one engine per process, `expire_on_commit=False` for web code, and 2.0-style `select()` queries. Fourth, **treat Alembic autogenerate as a draft**. Every example below was type-checked under pyright strict on Python 3.14 and run against a real PostgreSQL 16 database for this report. Those tests show that autogenerate and `alembic check` miss new enum values and edited CHECK expressions. The default autogenerated downgrade also leaves a native enum type behind, so a down-then-up round trip fails. Two typing gaps remain. The default ORM constructor cannot be type-checked (`User(emial="x")` passes pyright), and the only official fix is `MappedAsDataclass`. Python 3.14's lazy annotations do not stop SQLAlchemy from evaluating annotations at runtime, so cross-module relationship targets should stay quoted, and Ruff must be told about your declarative base. Several choices are genuinely open: staying on 2.0 or moving to 2.1, plain mapped classes or dataclass mappings, native enums or text plus CHECK, and helper functions or alembic-postgresql-enum. The report sets out each one rather than picking silently.

## SQLAlchemy 2.1 and Alembic 1.20 set the late-2026 baseline

**SQLAlchemy 2.1.0 shipped on 24 September 2026, and 2.1.3 followed on 2 October** ([2.1 changelog](https://docs.sqlalchemy.org/en/21/changelog/changelog_21.html)). It requires Python 3.11 or later and carries classifiers through 3.15 ([PyPI SQLAlchemy](https://pypi.org/project/SQLAlchemy/#history)). The migration guide gives the reason for the floor: "Python 3.10 is dropped as of August, 2026 in preparation for Python 3.10 EOL in October of 2026" ([What's New in 2.1](https://docs.sqlalchemy.org/en/21/changelog/migration_21.html)). The 2.0 series continues at **2.0.54 (15 September 2026)**, and the documentation site labels it the "legacy version" ([Declarative Table, 2.0](https://docs.sqlalchemy.org/en/20/orm/declarative_tables.html)). For declarations, 2.1 mostly tightens behaviour rather than adding syntax. A `NewType` without a `type_annotation_map` entry, and a PEP 695 alias that points at another alias, both warn in 2.0 and **fail in 2.1** ([Declarative Table](https://docs.sqlalchemy.org/en/20/orm/declarative_tables.html)). The changes that matter under pyright strict are elsewhere. They are listed in the table below.

| Concern | Stay on 2.0.x | Move to 2.1.x |
|---|---|---|
| Status | Supported, labelled "legacy" | Current stable line |
| Python floor | Works on 3.14 | 3.11+ |
| Bare `postgresql://` URL | psycopg2 | **psycopg 3** |
| Result rows under pyright | `Row[tuple[UUID, str]]`; unpacked values are `Any` (verified) | `Row[UUID, str]`; unpacked values are `UUID` and `str` (verified) |
| `Result.tuples()`, `Row._t` | The documented typing workaround | **Deprecated since 2.1.0** (verified in the 2.1.0 and 2.1.3 tags) |
| Autoflush | Skipped before `text()` | Unconditional before every execute |
| Dataclass mappings | `default` and `insert_default` combinable | Mutually exclusive; new `DONT_SET` default semantics |
| mypy plugin | Deprecated; mypy ≤ 1.10.1 only | Removed |
| `greenlet` | Installed by default | Only via `sqlalchemy[asyncio]` |
| Python 3.14 t-strings | No | `tstring(t"...")` |

The sources for that table are the 2.1 migration guide and changelog ([What's New in 2.1](https://docs.sqlalchemy.org/en/21/changelog/migration_21.html), [2.1 changelog](https://docs.sqlalchemy.org/en/21/changelog/changelog_21.html)), plus the `@deprecated("2.1.0", ...)` decorators on `Result.tuples()`, `Result.t`, `Row._tuple()` and `Row._t` in the released source ([result.py at rel_2_1_3](https://github.com/sqlalchemy/sqlalchemy/blob/rel_2_1_3/lib/sqlalchemy/engine/result.py)). I found no mention of the `tuples()` deprecation in the migration guide. It surfaced only because the test suite ran with warnings as errors. **The strongest typing argument for 2.1 is the PEP 646 row typing.** Under 2.0, `for task_id, title in session.execute(select(Task.id, Task.title))` gives pyright two `Any` values. Under 2.1 the same loop gives `UUID` and `str`, typed for up to 10 selected expressions ([What's New in 2.1: Row typing](https://docs.sqlalchemy.org/en/21/changelog/migration_21.html#row-now-represents-individual-column-types-directly-without-tuple)). The argument for staying on 2.0 is purely operational: the upgrade changes the default driver, and it changes autoflush timing before raw `text()` statements.

**The driver change is the upgrade's main trap.** The 2.1 guide's section "Default PostgreSQL driver changed to psycopg (psycopg 3)" calls `postgresql+psycopg://` "(preferred)". It says psycopg2 "remains fully supported" through `postgresql+psycopg2://` ([What's New in 2.1: Default PostgreSQL driver](https://docs.sqlalchemy.org/en/21/changelog/migration_21.html#default-postgresql-driver-changed-to-psycopg-psycopg-3)). Projects that relied on a bare URL broke when 2.1 landed: one issue reports that "a bare `postgresql://` now selects psycopg 3" ([LLMHub #102](https://github.com/Center-for-AI-Innovation/LLMHub/issues/102)), and another says its build broke "since 2026-09-26" ([TFactory #1334](https://github.com/olafkfreund/TFactory/issues/1334)). psycopg2's own PyPI page says it "is not expected to receive new features" and tells new projects to "start from 3" ([PyPI psycopg2-binary](https://pypi.org/project/psycopg2-binary/)). psycopg 3.3.6 (18 September 2026) supports Python 3.10 to 3.15 ([PyPI psycopg](https://pypi.org/project/psycopg/)). **Name the driver in the URL whichever SQLAlchemy line you run.** For sync code, move to psycopg 3 now. asyncpg (0.31.0) matters only for async engines ([PyPI asyncpg](https://pypi.org/project/asyncpg/)).

**Alembic 1.20.0 (11 September 2026) made SQLAlchemy 2.0 its minimum.** Its other recent releases changed several defaults ([Alembic changelog](https://alembic.sqlalchemy.org/en/latest/changelog.html)). Version 1.16 added optional `pyproject.toml` configuration and `path_separator`, and 1.16.3 added a `module` post-write hook runner "for tools like ruff". Version 1.17 requires Python 3.10, and 1.18 reorganised autogenerate into plugins selected with `autogenerate_plugins`. Version 1.19.0 turned on name-based CHECK-constraint detection by default, and **1.19.2 made it opt-in again**. Avoid 1.19.0 and 1.19.1 unless you want that detection on. `compare_type` has defaulted to `True` since 1.12 ([Alembic runtime API](https://alembic.sqlalchemy.org/en/latest/api/runtime.html)). A sensible pin set looks like this:

```toml
# pyproject.toml (excerpt)
[project]
requires-python = ">=3.14"
dependencies = [
    "sqlalchemy>=2.1.3,<2.2",   # or "sqlalchemy>=2.0.54,<2.1" if you stay on 2.0
    "alembic>=1.20,<1.21",
    "psycopg[binary]>=3.3",
    "geoalchemy2>=0.20",        # only for PostGIS
]
```

**No plugin, and no third-party stubs.** The SQLAlchemy docs say: "The SQLAlchemy Mypy Plugin is DEPRECATED, and will be removed in the SQLAlchemy 2.1 release." The plugin only works up to mypy 1.10.1. The docs point users to the inline PEP 484 typing instead, which also serves pyright, Pylance and PyCharm ([Mypy / PEP 484 support](https://docs.sqlalchemy.org/en/20/orm/extensions/mypy.html)). `DeclarativeBase` "integrates with PEP 484 tools without the use of plugins" ([Declarative Mapping Styles](https://docs.sqlalchemy.org/en/20/orm/declarative_styles.html)).

**How the examples were verified.** PyPI was blocked from the research sandbox, so packages were assembled from source: SQLAlchemy at the `rel_2_0` and `main` branch heads (2.0.55.dev and 2.1.4.dev), Alembic 1.20.1.dev, psycopg 3.3.7.dev (pure-Python, over libpq 16), GeoAlchemy2's main branch, and pytest. Every Python block in this report that starts with a file-path comment was type-checked with **pyright 1.1.414 in strict mode with `pythonVersion = "3.14"` against both SQLAlchemy lines, with zero errors**. The blocks were also run on CPython 3.14.6 against PostgreSQL 16.15. The test suite in the final sections passes on both lines with `-W error`. PostgreSQL 18-only features such as server-side `uuidv7()` were not exercised. GeoAlchemy2 was type-checked but not run.

## Annotations are the schema: `Mapped[]`, a type map and `Annotated` templates

`DeclarativeBase` supersedes `declarative_base()`. **Every column is `name: Mapped[T] = mapped_column(...)`, and the annotation drives both the Python type and the DDL** ([Declarative Mapping Styles](https://docs.sqlalchemy.org/en/20/orm/declarative_styles.html)). The nullability rules are mechanical: `Mapped[str]` is NOT NULL, `Mapped[str | None]` is NULL, `primary_key=True` implies NOT NULL, and an explicit `nullable=` always overrides the annotation ([Declarative Table](https://docs.sqlalchemy.org/en/20/orm/declarative_tables.html)). That last rule means `nullable=` should appear only when you *deliberately* want the annotation and the column to disagree. `Mapped[str] = mapped_column(nullable=True)` lets pyright treat a NULL column as `str`. A bare `Column(...)` on a declarative class types the attribute as `Column[int]`, not `int`. Neither belongs in new code.

The `type_annotation_map` on the base translates Python types into column types once. **An explicit type passed to `mapped_column()` still wins.** The docs' own example maps `datetime.datetime` to `TIMESTAMP(timezone=True)` ([Declarative Table](https://docs.sqlalchemy.org/en/20/orm/declarative_tables.html)). `Annotated` aliases act as reusable column templates. An inline `mapped_column()` merges with the template, and the inline arguments win on conflict. PEP 695 `type` aliases are supported from 2.0.37. **2.0.44** added implicit resolution of aliases whose target is in the map, and generic aliases with `Annotated` ([Declarative Table](https://docs.sqlalchemy.org/en/20/orm/declarative_tables.html)). The base below pins 2.0.44 in a comment to be safe. It follows the docs' patterns with two additions. It maps every `enum.Enum` to a value-storing type, and it uses Python 3.14's `uuid.uuid7` for primary keys:

```python
# app/db/base.py
"""Declarative base, naming convention, type map and reusable column types."""

import datetime
import enum
import uuid
from typing import Annotated, Any, Final

from sqlalchemy import Enum as SAEnum
from sqlalchemy import MetaData, func
from sqlalchemy.dialects.postgresql import JSONB, TIMESTAMP
from sqlalchemy.orm import DeclarativeBase, mapped_column
from sqlalchemy.types import Text

NAMING_CONVENTION: Final[dict[str, str]] = {
    "ix": "ix_%(column_0_label)s",
    "uq": "uq_%(table_name)s_%(column_0_N_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}


def enum_values(enum_cls: type[enum.Enum]) -> list[str]:
    """Persist each member's value ('in_progress'), not its name ('IN_PROGRESS')."""
    return [str(member.value) for member in enum_cls]


class BaseDB(DeclarativeBase):
    metadata = MetaData(naming_convention=NAMING_CONVENTION)
    type_annotation_map = {
        datetime.datetime: TIMESTAMP(timezone=True),
        dict[str, Any]: JSONB,
        enum.Enum: SAEnum(enum.Enum, values_callable=enum_values),
        str: Text(),
    }


# Reusable column "templates" (PEP 695 aliases need SQLAlchemy >= 2.0.44).
type UuidPK = Annotated[uuid.UUID, mapped_column(primary_key=True, default=uuid.uuid7)]
type CreatedAt = Annotated[datetime.datetime, mapped_column(server_default=func.now())]
type UpdatedAt = Annotated[
    datetime.datetime,
    mapped_column(onupdate=func.now(), server_default=func.now()),
]
```

Under pyright strict, **`metadata`, `type_annotation_map` and `__table_args__` need no annotations**. `DeclarativeBase` already declares them, and `__table_args__` is declared as `Any`. Annotating `__table_args__` as `tuple[Any, ...]` is harmless documentation. Leaving it out was also clean in testing. The named `enum_values` function replaces the docs' `lambda x: [i.value for i in x]`, so strict mode has no unannotated lambda parameter to infer.

### Naming conventions make every constraint addressable

**Put the documented naming convention on the base's `MetaData`, and name every `CheckConstraint` explicitly**, because the `ck` template needs `%(constraint_name)s`. The convention fixes names "at Python construction time, rather than at DDL emit time". As a result, "the naming convention will be explicit when a new migration script is generated" ([Constraints and Indexes](https://docs.sqlalchemy.org/en/20/core/constraints.html)). Without it, PostgreSQL invents names such as `user_order_user_account_id_fkey` that migrations cannot reliably refer to ([Alembic naming docs](https://alembic.sqlalchemy.org/en/latest/naming.html)).

The docs' `uq` template names only the first column. The base above uses the documented `%(column_0_N_name)s` token, which joins all column names with underscores. That keeps multi-column unique constraints distinguishable, at the cost of approaching PostgreSQL's 63-character identifier limit sooner. Enum *types* are not constraints, so give each one an explicit `name=`.

### PostgreSQL types: timestamptz, UUIDv7, JSONB and value-storing enums

SQLAlchemy's docs say CamelCase types are "to the greatest degree possible database agnostic", while UPPERCASE types render "exactly as given" ([Type Hierarchy](https://docs.sqlalchemy.org/en/20/core/type_basics.html)). For a PostgreSQL-only codebase both are legitimate. **Generic types inferred from annotations keep models quiet. Dialect types belong in the type map, or on columns with no generic equivalent** (`JSONB`, `TSVECTOR`, range types, `ExcludeConstraint`). For timestamps, the docs recommend the `TIMESTAMP` type directly when you use `timezone=True` ([Type Hierarchy, 2.1](https://docs.sqlalchemy.org/en/21/core/type_basics.html)). Store `timestamptz` and keep Python datetimes timezone-aware. PostgreSQL's `TimeZone` setting only "sets the time zone for displaying and interpreting time stamps" ([PostgreSQL client configuration](https://www.postgresql.org/docs/current/runtime-config-client.html)). In testing, a `-c timezone=UTC` connection option made psycopg 3 return values with `tzinfo=datetime.timezone.utc`. `REAL` is a 32-bit float ([Type Hierarchy](https://docs.sqlalchemy.org/en/20/core/type_basics.html)). Use `Numeric` for money and `Double` for general floating point.

`Mapped[uuid.UUID]` maps to the generic `Uuid` type, which uses the native `uuid` type on PostgreSQL ([Type Hierarchy, 2.1](https://docs.sqlalchemy.org/en/21/core/type_basics.html)). There are three ways to generate primary keys. **Python 3.14's `uuid.uuid7()`** embeds a 48-bit timestamp and "a 42-bit counter to guarantee monotonicity within a millisecond" ([Python uuid docs](https://docs.python.org/3.14/library/uuid.html)). Python-side generation keeps IDs known before flush and works on any PostgreSQL version. **PostgreSQL 18's `uuidv7()`** is the server-side alternative ([PostgreSQL 18 UUID functions](https://www.postgresql.org/docs/18/functions-uuid.html)). SQLAlchemy 2.1 accepts `server_default=func.uuidv7(monotonic=True)`, which "allows Core and ORM to use a more efficient batched form of INSERT" ([2.1 PostgreSQL dialect](https://docs.sqlalchemy.org/en/21/dialects/postgresql.html#postgresql-18-and-above-uuid-with-uuidv7-as-a-server-default)). **`uuid4`** remains right wherever leaking creation time matters, because a v7 UUID's timestamp can be read back with `uuid_extract_timestamp()`. Integer keys should use `Identity()`, which "supersedes the use of SERIAL" on PostgreSQL 10 and later ([2.1 PostgreSQL dialect](https://docs.sqlalchemy.org/en/21/dialects/postgresql.html)).

JSON and ARRAY columns do not track in-place mutation. The docs say "The JSON type, when used with the SQLAlchemy ORM, does not detect in-place mutations to the structure". Wrap the column in `MutableDict`/`MutableList`, or reassign the value ([Type Hierarchy, 2.1](https://docs.sqlalchemy.org/en/21/core/type_basics.html)). `Mapped[dict[str, Any]]` is the honest annotation. A `TypedDict` documents the shape, but SQLAlchemy does not validate it.

**Enums need deliberate configuration, because SQLAlchemy stores member names by default.** `Mapped[MyEnum]` maps to `sqlalchemy.Enum(MyEnum)`, a native `CREATE TYPE` on PostgreSQL. The docs state: "the string names of each element ... are persisted to the database; the values of the Python Enum ... are **not** used." `values_callable` changes that ([Type Hierarchy](https://docs.sqlalchemy.org/en/20/core/type_basics.html)). A `StrEnum` such as `IN_PROGRESS = "in_progress"` would therefore store `'IN_PROGRESS'` without it. Testing settled a question the docs leave open. **A generic `enum.Enum: SAEnum(enum.Enum, values_callable=enum_values)` entry in the type map applies `values_callable` to every enum**, and the rendered type contained `'done', 'in_progress', 'todo'`. The type was named after the lowercased class (`taskstatus`), though, so per-column `SAEnum(..., name="task_status")` is still needed when names matter. `typing.Literal` maps to a non-native VARCHAR enum instead ([Declarative Table](https://docs.sqlalchemy.org/en/20/orm/declarative_tables.html)). The model below combines these choices with a named CHECK, a partial index and a typed hybrid property:

```python
# app/models/task.py
import datetime
import enum
import uuid
from typing import TYPE_CHECKING, Any

from sqlalchemy import CheckConstraint, ColumnElement, ForeignKey, Index, text
from sqlalchemy import Enum as SAEnum
from sqlalchemy.ext.hybrid import hybrid_property
from sqlalchemy.orm import Mapped, mapped_column, relationship

from app.db.base import BaseDB, CreatedAt, UpdatedAt, UuidPK, enum_values

if TYPE_CHECKING:
    from app.models.project import Project


class TaskStatus(enum.StrEnum):
    DONE = "done"
    IN_PROGRESS = "in_progress"
    TODO = "todo"


class Task(BaseDB):
    __tablename__ = "tasks"
    __table_args__: tuple[Any, ...] = (
        CheckConstraint("priority BETWEEN 1 AND 5", name="priority_range"),
        Index(
            "ix_tasks_project_id_open",
            "project_id",
            postgresql_where=text("completed_at IS NULL"),
        ),
    )

    completed_at: Mapped[datetime.datetime | None]
    created_at: Mapped[CreatedAt]
    id: Mapped[UuidPK]
    priority: Mapped[int] = mapped_column(server_default="3")
    project: Mapped["Project"] = relationship(back_populates="tasks", lazy="raise")
    project_id: Mapped[uuid.UUID] = mapped_column(
        ForeignKey("projects.id", ondelete="CASCADE"), index=True
    )
    status: Mapped[TaskStatus] = mapped_column(
        SAEnum(TaskStatus, name="task_status", values_callable=enum_values),
        server_default=TaskStatus.TODO.value,
    )
    title: Mapped[str] = mapped_column(index=True)
    updated_at: Mapped[UpdatedAt]

    @hybrid_property
    def is_open(self) -> bool:
        return self.completed_at is None

    @is_open.inplace.expression
    @classmethod
    def _is_open_expression(cls) -> ColumnElement[bool]:
        return cls.completed_at.is_(None)
```

The hybrid uses `.inplace` (added in 2.0.4). The docs explain that the classic `@prop.setter def prop` redefinition defeats type checkers, and that expression methods should return `ColumnElement[T]` ([Hybrid Attributes](https://docs.sqlalchemy.org/en/20/orm/extensions/hybrid.html)). Columns are in alphabetical order with relationships interleaved. That is harmless, because DDL column order follows the declared columns only. Other PostgreSQL constructs are dialect keywords: `postgresql_using="gin"`, `postgresql_include=[...]`, `postgresql_ops`, `postgresql_concurrently=True`, and `ExcludeConstraint` ([2.1 PostgreSQL dialect](https://docs.sqlalchemy.org/en/21/dialects/postgresql.html)).

### Defaults belong on the server, and RETURNING brings them back

`default=` and `onupdate=` run in Python and never reach the DDL. **`server_default=` is emitted in `CREATE TABLE` and is visible to Alembic.** `server_onupdate=` emits no DDL at all; it only marks a column as database-maintained ([Column INSERT/UPDATE Defaults](https://docs.sqlalchemy.org/en/20/core/defaults.html)). The docs show both styles. The mixin example uses client-side `default=func.now()`, while the `Annotated` timestamp example uses `server_default`. **For a migrations-managed PostgreSQL schema, prefer `server_default`**, because raw-SQL inserts and other clients get the same values. That is why `CreatedAt` above uses it. PostgreSQL has no `ON UPDATE` column clause. `updated_at` therefore needs either `onupdate=func.now()` or a trigger paired with `server_onupdate=FetchedValue()`.

The usual objection is that a server default leaves the attribute unloaded after flush. That no longer holds on PostgreSQL. `Mapper.eager_defaults` defaults to `"auto"`, which fetches server defaults for INSERT "using RETURNING if the backing database supports it" ([Mapper API](https://docs.sqlalchemy.org/en/20/orm/mapping_api.html#sqlalchemy.orm.Mapper.params.eager_defaults)). In testing, flushing a new `User` emitted `INSERT ... RETURNING users.created_at, users.updated_at`, with no follow-up SELECT. The values were loaded and timezone-aware immediately after `flush()`. Column mixins no longer need `declared_attr`, even with a `ForeignKey`, since 2.0 ([Mixins](https://docs.sqlalchemy.org/en/20/orm/declarative_mixins.html)). Relationships on mixins still need `@declared_attr` with a `Mapped[...]` return annotation, and `__tablename__` and `__table_args__` directives need `@declared_attr.directive`. The `Annotated` aliases above achieve the same reuse without inheritance.

## Two typing gaps remain: runtime-evaluated annotations and the constructor

### Python 3.14 defers annotations, but SQLAlchemy still reads them

PEP 749 keeps `from __future__ import annotations` working in 3.14. It will be deprecated once 3.13 reaches end of life: "After at least two releases, the future import is removed, and annotations are always evaluated as per PEP 649" ([PEP 749](https://peps.python.org/pep-0749/)). **New code should not add the import.** But `Mapped[...]` is evaluated at runtime when the class is mapped. Mergify's PEP 649 write-up lists SQLAlchemy among the libraries that "inspect annotations at runtime" ([Mergify blog](https://mergify.com/blog/python-314-what-pep-649-actually-breaks)). SQLAlchemy also fixed a 3.14 bug: annotation errors were mishandled when no future import was present, because the code assumed a `NameError` could only come from string annotations ([sqlalchemy#13602](https://github.com/sqlalchemy/sqlalchemy/issues/13602)).

The tests for this report settled how forward references behave on 3.14 without the future import. Relationship targets imported only under `TYPE_CHECKING` resolved at mapping time on both lines, whether quoted (`Mapped[list["Project"]]`) or unquoted (`Mapped[list[Project]]`), because SQLAlchemy looks class names up in its registry. **Any other type imported only under `TYPE_CHECKING` breaks mapping.** A `uuid` import moved into that block raised `MappedAnnotationError: Could not resolve all types within mapped annotation` on both 2.0 and 2.1.

That interacts badly with Ruff's defaults. Its `TC003` rule tells you to move `uuid` and `datetime` imports into `TYPE_CHECKING` blocks, which is exactly the change that breaks mapping. Its `UP037` rule tells you to remove quotes. Ruff's fix is a setting for "libraries like SQLAlchemy and Pydantic that use metaclasses or other runtime mechanisms" ([Ruff settings](https://docs.astral.sh/ruff/settings/#lint_flake8-type-checking_runtime-evaluated-base-classes)). In testing, though, **listing only `sqlalchemy.orm.DeclarativeBase` was not enough**, because Ruff does not follow inheritance across modules. Your own base must be listed too:

```toml
# pyproject.toml (excerpt)
[tool.ruff.lint.flake8-type-checking]
runtime-evaluated-base-classes = ["sqlalchemy.orm.DeclarativeBase", "app.db.base.BaseDB"]
```

With that setting, Ruff flags an *unquoted* `TYPE_CHECKING`-imported target with `TC004` and accepts a quoted one. The consistent rule follows from that. **Quote cross-module relationship targets, import every other annotation type at runtime, and never add the future import.** This is the one place where SQLAlchemy code departs from the general Python 3.14 advice to drop quoted forward references. Same-module forward references, such as `Mapped[list[Workspace]]` before `Workspace` is defined, worked unquoted in testing.

### The constructor is the one hole pyright cannot see

**On a plain `DeclarativeBase` model, pyright accepts `User(emial="x")` and `User()` without complaint.** The ORM generates `__init__` at runtime, so attribute access is typed but construction is not. A SQLAlchemy maintainer put it this way: "To have an init constructed you should use a dataclass ... There is no other way of dynamically generating an init so that type checker can understand it" ([sqlalchemy#12268](https://github.com/sqlalchemy/sqlalchemy/issues/12268)). `MappedAsDataclass` uses PEP 681 `dataclass_transform`, so pyright checks the generated `__init__`. It brings its own rules ([Integration with dataclasses](https://docs.sqlalchemy.org/en/20/orm/dataclasses.html)). Per-field `init`, `default`, `default_factory`, `repr` and `kw_only` must be passed inline, not inside `Annotated`. `insert_default` carries the column default, so that `default` can mean the constructor default. Collections need `default_factory=list`, mixins must themselves be dataclass mixins, and `frozen` and `slots` are unsupported. 2.1 changes the semantics again: defaults are delivered through descriptors, `default` and `insert_default` become mutually exclusive, and a relationship `default` may only be `None` on a many-to-one ([What's New in 2.1](https://docs.sqlalchemy.org/en/21/changelog/migration_21.html)).

Alphabetical column order collides with the dataclass rule that required fields precede defaulted ones. `kw_only=True` resolves the collision, but testing found a catch. **Passing `kw_only=True` on the base made the runtime constructors keyword-only, yet pyright did not inherit it.** Pyright reported "Fields without default values cannot appear after fields with default values" on each subclass. Passing it on every mapped class fixes that, and pyright then flags both the missing `email` and the misspelled `emial`:

```python
# app/models_dataclass.py
"""Option B: MappedAsDataclass for a type-checked constructor."""

import datetime
import uuid

from sqlalchemy import ForeignKey, String, func
from sqlalchemy.orm import DeclarativeBase, Mapped, MappedAsDataclass, mapped_column, relationship


class BaseDC(MappedAsDataclass, DeclarativeBase):
    """Pass kw_only=True on every mapped class: pyright does not inherit it."""


class Owner(BaseDC, kw_only=True):
    __tablename__ = "owners"

    created_at: Mapped[datetime.datetime] = mapped_column(init=False, server_default=func.now())
    email: Mapped[str] = mapped_column(String(320), unique=True)
    id: Mapped[uuid.UUID] = mapped_column(default_factory=uuid.uuid7, primary_key=True)
    nickname: Mapped[str | None] = mapped_column(default=None)
    workspaces: Mapped[list[Workspace]] = relationship(back_populates="owner", default_factory=list)


class Workspace(BaseDC, kw_only=True):
    __tablename__ = "workspaces"

    id: Mapped[uuid.UUID] = mapped_column(default_factory=uuid.uuid7, primary_key=True)
    name: Mapped[str]
    owner: Mapped[Owner | None] = relationship(back_populates="workspaces", default=None)
    owner_id: Mapped[uuid.UUID | None] = mapped_column(ForeignKey("owners.id"), default=None)


def build() -> Owner:
    owner = Owner(email="a@example.com")
    owner.workspaces.append(Workspace(name="w"))
    return owner
```

There are three options. **Plain mapped classes** are the documented default with the fewest rules, and they leave construction unchecked. **`MappedAsDataclass`** closes the hole at the cost of per-field dataclass arguments, a `kw_only=True` on every class, and 2.1's changed default semantics. **Typed factory functions or classmethods** check construction for the call sites that matter, with no change to the mapping, but nothing forces callers to use them. Under a "pyright strict is the CI gate" policy, the dataclass route is the only one that makes every constructor call a checked call.

## Relationships load nothing implicitly once `lazy="raise"` is on

The docs' relationship patterns translate directly into typed code. One-to-many is `Mapped[list["Child"]] = relationship(back_populates="parent")`, and many-to-one is `Mapped["Parent"]`, or `Mapped["Parent | None"]` over a nullable foreign key. The annotation picks the collection type, so `uselist=` is unnecessary, and many-to-many passes an association `Table` as `secondary=` ([Basic Relationship Patterns](https://docs.sqlalchemy.org/en/20/orm/basic_relationships.html)). **`back_populates` replaces `backref`, which has its own "legacy" page.** `backref` also creates an attribute pyright cannot see. 2.1 adds `back_populates=lambda: B.a` for refactor-safe references ([What's New in 2.1](https://docs.sqlalchemy.org/en/21/changelog/migration_21.html)). For large collections, `WriteOnlyMapped` replaces `lazy="dynamic"`, which the docs call "the legacy form of what is now the 'write_only' strategy" ([Working with Large Collections](https://docs.sqlalchemy.org/en/20/orm/large_collections.html)). Pair `cascade="all, delete-orphan"` and `passive_deletes=True` with `ForeignKey(..., ondelete="CASCADE")` so the database deletes children without the ORM loading them first:

```python
# app/models/project.py
import uuid
from typing import TYPE_CHECKING, Any

from sqlalchemy import ForeignKey
from sqlalchemy.dialects.postgresql import JSONB
from sqlalchemy.ext.mutable import MutableDict
from sqlalchemy.orm import Mapped, mapped_column, relationship

from app.db.base import BaseDB, CreatedAt, UpdatedAt, UuidPK

if TYPE_CHECKING:
    from app.models.task import Task
    from app.models.user import User


class Project(BaseDB):
    __tablename__ = "projects"

    created_at: Mapped[CreatedAt]
    id: Mapped[UuidPK]
    name: Mapped[str]
    owner: Mapped["User"] = relationship(back_populates="projects", lazy="raise")
    owner_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("users.id", ondelete="CASCADE"))
    settings: Mapped[dict[str, Any]] = mapped_column(
        MutableDict.as_mutable(JSONB), default=dict, server_default="{}"
    )
    slug: Mapped[str] = mapped_column(unique=True)
    tasks: Mapped[list["Task"]] = relationship(
        back_populates="project",
        cascade="all, delete-orphan",
        lazy="raise",
        passive_deletes=True,
    )
    updated_at: Mapped[UpdatedAt]
```

Lazy loading is the default, and the official guidance on which loader to use instead is direct. For collections, "`selectinload()` is generally the best loading strategy to use". For many-to-one, "`joinedload()` strategy is the most general purpose strategy". `subqueryload` is "mostly legacy", and raiseload "replaces the behavior of lazy loading with an informative error being raised" ([Relationship Loading Techniques](https://docs.sqlalchemy.org/en/20/orm/queryguide/relationships.html#what-kind-of-loading-to-use)).

**Setting `lazy="raise"` on every relationship turns every accidental N+1 into a test failure.** It also guarantees that converting ORM objects into Pydantic entities never issues hidden SQL. The docs present it as an option, recommended specifically for asyncio ([Preventing Implicit IO](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#preventing-implicit-io-when-using-asyncsession)), not as a mandate. The lighter alternative is `raiseload("*")` at each query site. In the test suite, touching an unloaded `task.project` raised `InvalidRequestError` as intended. In 2.1, when one object is reached by several loader paths, "the shallowest path is favored". `noload()` is deprecated ([2.1 changelog](https://docs.sqlalchemy.org/en/21/changelog/changelog_21.html)).

## Sessions belong to the caller, and one engine serves the whole process

The Session FAQ is unambiguous: "keep the lifecycle of the session **separate and external** from functions and objects that access and/or manipulate database data", and "keep transactions **short**". Its "wrong way" example is a data-access class that creates and commits its own session. Its better way passes the session in and frames the work in the caller ([Session Basics FAQ](https://docs.sqlalchemy.org/en/20/orm/session_basics.html#when-do-i-construct-a-session-when-do-i-commit-it-and-when-do-i-close-it)). For web apps it suggests creating a Session per request and committing at the end of writes. It adds: "It's also usually a good idea to set Session.expire_on_commit to False". **So facades take a `Session`, may `flush()`, and never `commit()`.** Routes, services or scripts own the transaction. Which of those layers commits is a separate choice. FastAPI's tutorial commits in the route, while the FAQ frames the transaction around the caller. Either satisfies SQLAlchemy's rule.

There should be one `Engine` and one `sessionmaker` per process, created at module scope. The engine is "most efficient when created just once at the module level ... not per-object or per-function call" ([Working with Engines](https://docs.sqlalchemy.org/en/20/core/connections.html)). For forked workers, the docs call `engine.dispose(close=False)` in the child initializer "the recommended approach" ([Pooling with multiprocessing](https://docs.sqlalchemy.org/en/20/core/pooling.html#using-connection-pools-with-multiprocessing-or-os-fork)). `pool_pre_ping=True` is "the most simple and reliable approach" to stale connections. It does not cover connections that drop mid-transaction ([Disconnect Handling](https://docs.sqlalchemy.org/en/20/core/pooling.html#disconnect-handling-pessimistic)). **The default pool of 5 plus 10 overflow is undersized for FastAPI's sync threadpool.** AnyIO's default limiter allows 40 worker threads per process ([AnyIO threads](https://anyio.readthedocs.io/en/stable/threads.html)), so up to 25 concurrent `def` requests per worker can wait out `pool_timeout`. The total across workers, scripts and Alembic must still fit under PostgreSQL's `max_connections`, which "is typically 100" ([PostgreSQL connection settings](https://www.postgresql.org/docs/current/runtime-config-connection.html)).

Session-level settings can travel in libpq's `options` string, which "specifies command-line options to send to the server at connection start" ([libpq connection parameters](https://www.postgresql.org/docs/current/libpq-connect.html)). PostgreSQL's docs advise against setting `statement_timeout` or `lock_timeout` in `postgresql.conf`, because that "would affect all sessions" ([PostgreSQL client configuration](https://www.postgresql.org/docs/current/runtime-config-client.html)). The `options` string is a libpq mechanism, not a documented SQLAlchemy recipe. SQLAlchemy's own documented shape is a `connect` event that issues `SET SESSION` with autocommit toggled ([PostgreSQL search_path recipe](https://docs.sqlalchemy.org/en/20/dialects/postgresql.html#setting-alternate-search-paths-on-connect)). Only the `options` string was tested here: through psycopg 3, `SHOW` returned `UTC`, `30s` and `5s`.

```python
# app/db/engine.py
"""One Engine and one sessionmaker per process, created at import time."""

import os
from collections.abc import Iterator

from sqlalchemy import Engine, create_engine
from sqlalchemy.orm import Session, sessionmaker

DATABASE_URL: str = os.environ.get(
    "DATABASE_URL", "postgresql+psycopg://postgres@localhost:55432/app"
)

engine: Engine = create_engine(
    DATABASE_URL,
    pool_pre_ping=True,
    pool_size=10,
    max_overflow=20,
    connect_args={
        "application_name": "app-api",
        "options": "-c timezone=UTC -c statement_timeout=30s -c lock_timeout=5s",
    },
)
SessionLocal: sessionmaker[Session] = sessionmaker(engine, expire_on_commit=False)


def get_db() -> Iterator[Session]:
    """FastAPI dependency: one plain Session per request, closed afterwards."""
    with SessionLocal() as session:
        yield session


def dispose_after_fork() -> None:
    """Call in a post-fork hook or multiprocessing initializer."""
    engine.dispose(close=False)
```

**Keep `scoped_session` out of request handling.** The docs call it "only one approach". They warn that the thread-local registry "is not necessarily compatible with all application servers", and they "strongly recommend" framework integration that ties the Session "directly with the request, rather than with the current thread" ([Contextual Sessions](https://docs.sqlalchemy.org/en/20/orm/contextual.html)). The asyncio page goes further: "SQLAlchemy generally does not recommend the 'scoped' pattern for new development" ([asyncio scoped session](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#using-asyncio-scoped-session)). FastAPI confirms that "one single request could use more than one thread" ([FastAPI SQL Databases](https://fastapi.tiangolo.com/tutorial/sql-databases/)). A maintainer also confirmed that a dependency and its route can run on different threads ([fastapi #6069](https://github.com/fastapi/fastapi/discussions/6069)). A thread-local session can therefore hand a route a different Session from the one its dependency closes. For single-threaded scripts and cron jobs, a registry is within documented use, provided `remove()` runs in a `finally`. Even there, the facade should still receive the session explicitly:

```python
# app/jobs.py
"""Scripts and cron jobs: a thread-local registry is acceptable outside requests."""

import uuid

from sqlalchemy.orm import Session, scoped_session

from app.db.engine import SessionLocal
from app.facades.tasks import complete_tasks

ScopedSession: scoped_session[Session] = scoped_session(SessionLocal)


def close_project_job(project_id: uuid.UUID) -> int:
    try:
        session: Session = ScopedSession()
        closed = complete_tasks(session, project_id)  # facade still receives the session
        session.commit()
        return len(closed)
    finally:
        ScopedSession.remove()  # close and discard this thread's session
```

The Session lifecycle has four rules worth stating, all from the same Session Basics page ([Session Basics](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)). Autoflush runs before ORM queries, and `commit()` always flushes. After a failed flush the Session is "inactive" until you call `rollback()`. `Session.get()` is the only lookup that can skip SQL, through the identity map. In 2.1, autoflush also runs before Core and `text()` statements, so a facade that adds an object and then runs raw SQL sees that object's row in 2.1 but not in 2.0 ([What's New in 2.1: autoflush](https://docs.sqlalchemy.org/en/21/changelog/migration_21.html#session-autoflush-behavior-simplified-to-be-unconditional)).

**Async is optional, not best practice.** The concurrency rule is "Session per thread, AsyncSession per task" ([Is the Session thread-safe?](https://docs.sqlalchemy.org/en/20/orm/session_basics.html#is-the-session-thread-safe-is-asyncsession-safe-to-share-in-concurrent-tasks)). Async code needs `expire_on_commit=False`, eager loading or `AsyncAttrs`, and an explicitly passed `AsyncSession`. psycopg 3 serves both modes (`postgresql+psycopg_async://`). Nothing in the docs makes async a requirement for a sync FastAPI application.

## 2.1 types rows precisely and deprecates the 2.0 workarounds

The rules for queries are short. Use `select()` with `Session.scalars()` for entities, `Session.execute()` for multi-column rows, and `Session.get()` or `get_one()` for primary keys ([ORM Querying Guide](https://docs.sqlalchemy.org/en/20/orm/queryguide/select.html)). The legacy `Query` API "is **not being removed**", but it is now "just a very thin adapter" ([Legacy Query API](https://docs.sqlalchemy.org/en/20/orm/queryguide/query.html)). `.all()` returns `Sequence[T]`, not `list[T]`. Joined eager loading of collections needs `.unique()`. **For column tuples, unpack rows instead of calling `.tuples()` or `Row._t`.** Unpacking is typed on 2.1, free of deprecation warnings, and runs unchanged on 2.0, where pyright sees `Any`. Returning `Sequence[Row[UUID, str]]` is also typed on 2.1, but that annotation cannot be written for 2.0, where the same rows are `Row[tuple[UUID, str]]`. `Row._t` additionally trips pyright strict's `reportPrivateUsage`. `.mappings()` returns `RowMapping` objects whose values are `Any`. Named attribute access such as `row.title` "continue[s] to be typed as Any" even in 2.1 ([What's New in 2.1: Row typing](https://docs.sqlalchemy.org/en/21/changelog/migration_21.html#row-now-represents-individual-column-types-directly-without-tuple)).

Writes follow the documented ORM DML forms ([ORM-Enabled DML](https://docs.sqlalchemy.org/en/20/orm/queryguide/dml.html)). **Bulk INSERT** is `session.execute(insert(Model), [dicts])`, keyed by ORM attribute names; `bulk_insert_mappings()` is legacy and lacks RETURNING. **Upserts** use `postgresql.insert(...).on_conflict_do_update(...)`, built in two steps so that `stmt.excluded` can refer back to the statement, with `.returning(Model)` and `populate_existing` to get refreshed objects. **ORM `update()` and `delete()`** bypass the unit of work, and `synchronize_session` defaults to `'auto'`, which means `'fetch'` on PostgreSQL. One warning is easy to miss: `on_conflict_do_update` "does **not** take into account Python-side default UPDATE values or generation functions" such as `onupdate` ([PostgreSQL ON CONFLICT](https://docs.sqlalchemy.org/en/20/dialects/postgresql.html#the-set-clause)). The upsert below therefore sets `updated_at` explicitly. Targeting the natural key's named constraint makes the upsert race-free, which a read-then-write sequence is not. The savepoint loop follows the docs' description of the pattern as "ideal for situations such as using PostgreSQL and catching IntegrityError" ([Using SAVEPOINT](https://docs.sqlalchemy.org/en/20/orm/session_transaction.html#using-savepoint)). Raw SQL uses `text()` with bound parameters. Beware the documented trap that `:value::int` is *not* a bind parameter; use `CAST(:value AS int)` or `:value ::int` ([text()](https://docs.sqlalchemy.org/en/20/core/sqlelement.html#sqlalchemy.sql.expression.text)). Results from `text()` and 2.1's `tstring()` are untyped, so annotate the function's return type at that boundary.

```python
# app/facades/tasks.py
"""Data-access functions: receive a Session, never commit."""

import datetime
import uuid
from collections.abc import Sequence

from sqlalchemy import func, select, text, update
from sqlalchemy.dialects.postgresql import insert as pg_insert
from sqlalchemy.exc import IntegrityError
from sqlalchemy.orm import Session, joinedload, raiseload, selectinload

from app.models import Project, Task, TaskStatus, User


def get_project(session: Session, project_id: uuid.UUID) -> Project | None:
    return session.get(Project, project_id)


def find_user_by_email(session: Session, email: str) -> User | None:
    return session.scalars(select(User).where(User.email == email)).one_or_none()


def count_open_tasks(session: Session, project_id: uuid.UUID) -> int:
    stmt = select(func.count()).select_from(Task).where(
        Task.project_id == project_id, Task.is_open
    )
    return session.execute(stmt).scalar_one()


def projects_with_owner_and_tasks(session: Session) -> Sequence[Project]:
    stmt = (
        select(Project)
        .options(
            joinedload(Project.owner),  # many-to-one: joinedload
            selectinload(Project.tasks),  # collection: selectinload
            raiseload("*"),  # anything else raises instead of lazy-loading
        )
        .order_by(Project.name)
    )
    return session.scalars(stmt).all()


def task_titles(session: Session, project_id: uuid.UUID) -> list[tuple[uuid.UUID, str]]:
    """Unpack rows: portable to 2.1, where Result.tuples() and Row._t are deprecated."""
    stmt = select(Task.id, Task.title).where(Task.project_id == project_id)
    return [(task_id, title) for task_id, title in session.execute(stmt)]


def upsert_project(session: Session, *, name: str, owner_id: uuid.UUID, slug: str) -> Project:
    """Race-free upsert on the natural key; returns the ORM object."""
    stmt = pg_insert(Project).values(name=name, owner_id=owner_id, slug=slug)
    stmt = stmt.on_conflict_do_update(
        constraint="uq_projects_slug",
        set_={"name": stmt.excluded.name, "updated_at": func.now()},
    ).returning(Project)
    return session.scalars(stmt, execution_options={"populate_existing": True}).one()


def complete_tasks(session: Session, project_id: uuid.UUID) -> Sequence[uuid.UUID]:
    stmt = (
        update(Task)
        .where(Task.project_id == project_id, Task.is_open)
        .values(completed_at=func.now(), status=TaskStatus.DONE)
        .returning(Task.id)
    )
    return session.scalars(stmt).all()


def import_users(session: Session, emails: Sequence[str]) -> list[str]:
    """Insert each row in its own SAVEPOINT; skip duplicates without aborting."""
    skipped: list[str] = []
    for email in emails:
        try:
            with session.begin_nested():
                session.add(User(email=email))
        except IntegrityError:
            skipped.append(email)
    return skipped


def recent_task_ids(session: Session, since: datetime.datetime) -> Sequence[uuid.UUID]:
    stmt = text("SELECT id FROM tasks WHERE created_at >= :since").bindparams(since=since)
    return session.scalars(stmt).all()
```

`begin_nested()` flushes pending state before it emits the SAVEPOINT. An unrelated pending error therefore surfaces at the next savepoint, not where it was caused. One savepoint per row costs a round trip each, so for pure uniqueness conflicts a set-based `ON CONFLICT DO NOTHING` scales better.

## Alembic autogenerate writes drafts that miss enums, CHECKs and renames

**`env.py` should import `target_metadata` from a package that imports every model, and build the URL from application settings.** The Alembic naming docs pass the model `MetaData` as `target_metadata` ([Alembic naming](https://alembic.sqlalchemy.org/en/latest/naming.html)). Importing it from `app.models` rather than `app.db.base` gives pyright a used import while still registering every table. The runtime API documents the options this file sets. `include_name` filters by name before reflection, and `include_object` filters per object. `transaction_per_migration` defaults to `False`, but the docs recommend it whenever a migration uses `autocommit_block()` ([Alembic runtime API](https://alembic.sqlalchemy.org/en/latest/api/runtime.html)). The callback types used for annotation are real public names in 1.20: `NameFilterType` and `NameFilterParentNames` are importable from `alembic.runtime.environment`. The empty-revision suppression comes from the cookbook ([Alembic cookbook](https://alembic.sqlalchemy.org/en/latest/cookbook.html)).

```python
# migrations/env.py
"""Alembic environment: the URL and the metadata come from the application."""

from collections.abc import Iterable
from logging.config import fileConfig

from alembic import context
from alembic.operations.ops import MigrationScript
from alembic.runtime.environment import NameFilterParentNames, NameFilterType
from alembic.runtime.migration import MigrationContext
from sqlalchemy import Connection, MetaData, create_engine, pool, text
from sqlalchemy.schema import SchemaItem

from app.db.engine import DATABASE_URL
from app.models import BaseDB  # app.models imports every model module

config = context.config
if config.config_file_name is not None:
    fileConfig(config.config_file_name)

target_metadata: MetaData = BaseDB.metadata
IGNORED_TABLES: frozenset[str] = frozenset({"spatial_ref_sys"})


def database_url() -> str:
    override = config.attributes.get("database_url")
    return override if isinstance(override, str) else DATABASE_URL


def include_name(
    name: str | None, type_: NameFilterType, parent_names: NameFilterParentNames
) -> bool:
    if type_ == "table":
        return name not in IGNORED_TABLES
    return True


def include_object(
    obj: SchemaItem,
    name: str | None,
    type_: NameFilterType,
    reflected: bool,
    compare_to: SchemaItem | None,
) -> bool:
    if type_ == "column" and not reflected:
        return not obj.info.get("skip_autogenerate", False)
    return True


def process_revision_directives(
    context_: MigrationContext,
    revision: str | Iterable[str | None] | Iterable[str],
    directives: list[MigrationScript],
) -> None:
    """Do not write an empty revision file when autogenerate finds nothing."""
    cmd_opts = config.cmd_opts
    if cmd_opts is not None and getattr(cmd_opts, "autogenerate", False):
        script = directives[0]
        if all(ops.is_empty() for ops in script.upgrade_ops_list):
            directives[:] = []


def run_migrations_offline() -> None:
    context.configure(
        url=database_url(),
        target_metadata=target_metadata,
        literal_binds=True,
        dialect_opts={"paramstyle": "named"},
        transaction_per_migration=True,
    )
    with context.begin_transaction():
        context.run_migrations()


def do_run_migrations(connection: Connection) -> None:
    context.configure(
        connection=connection,
        target_metadata=target_metadata,
        compare_server_default=True,
        include_name=include_name,
        include_object=include_object,
        process_revision_directives=process_revision_directives,
        transaction_per_migration=True,
    )
    with context.begin_transaction():
        context.run_migrations()


def run_migrations_online() -> None:
    supplied = config.attributes.get("connection")
    if isinstance(supplied, Connection):
        do_run_migrations(supplied)
        return
    engine = create_engine(database_url(), poolclass=pool.NullPool)
    with engine.connect() as connection:
        connection.execute(text("SET lock_timeout = '5s'"))
        connection.execute(text("SET statement_timeout = 0"))
        connection.commit()  # session-level SETs outlive the commit
        do_run_migrations(connection)


if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()
```

Building the engine directly, rather than writing the URL into `config.set_main_option`, avoids configparser's `%` interpolation for URL-encoded passwords. In a real codebase, import the URL from your settings module. Importing the application's engine module, as here, constructs an unused engine as a side effect. `compare_server_default=True` departs from the default of `False`. On PostgreSQL the comparison is evaluated server-side ([Autogenerate docs](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)). In testing it reported **no false positives** for `now()`, `'3'`, `'todo'` and `'{}'`, and it caught a changed `server_default`. That makes it worth enabling when `alembic check` gates CI.

**The official migration templates still use `typing.Union` and `typing.Sequence`.** That holds for the `generic` template on main ([generic script.py.mako](https://github.com/sqlalchemy/alembic/blob/main/alembic/templates/generic/script.py.mako)) and for the `pyproject` template ([pyproject script.py.mako](https://github.com/sqlalchemy/alembic/blob/main/alembic/templates/pyproject/script.py.mako)), even though the 1.19 changelog notes PEP 604 unions in Alembic's own code. Ruff 0.16 flags the generated header with `UP035` and `UP007` when targeting Python 3.14. The Python docs mark these aliases as superseded by `X | Y` and `collections.abc` ([typing docs](https://docs.python.org/3/library/typing.html)). Ship a project template:

```mako
## migrations/script.py.mako
"""${message}

Revision ID: ${up_revision}

Create Date: ${create_date}
"""

from collections.abc import Sequence

import sqlalchemy as sa
from alembic import op
${imports if imports else ""}

revision: str = ${repr(up_revision)}
down_revision: str | Sequence[str] | None = ${repr(down_revision)}
branch_labels: str | Sequence[str] | None = ${repr(branch_labels)}
depends_on: str | Sequence[str] | None = ${repr(depends_on)}

    """Upgrade schema."""
    ${upgrades if upgrades else "pass"}

    ${downgrades if downgrades else "pass"}
```

In testing, the `## migrations/script.py.mako` line renders nothing. An empty revision from this template fails pyright strict with `reportUnusedImport` on `sa` and `op`. The Ruff `check --fix` hook below removes those imports, and the file then type-checks clean. The `ini` lines below set the remaining conventions. `path_separator = os` matters because "this default does NOT take place if path_separator is not present in alembic.ini" ([Alembic tutorial](https://alembic.sqlalchemy.org/en/latest/tutorial.html)). A date-prefixed `file_template` keeps files sortable. Since 1.18 it can also contain directories. The tutorial's own template documents a Ruff hook through the `module` runner (`ruff.type = module`, `ruff.options = check --fix REVISION_SCRIPT_FILENAME`), and the same pattern runs `ruff format`. Autogenerate emits single-quoted, long-line code that these hooks clean up. Moving the source settings into `[tool.alembic]` in `pyproject.toml` is optional, and `alembic.ini` "is still the default location for deployment details". If you use pyproject configuration, run 1.16.5 or later, which fixed its boolean parsing ([Alembic changelog](https://alembic.sqlalchemy.org/en/latest/changelog.html)).

```ini
# alembic.ini (excerpt)
[alembic]
script_location = %(here)s/migrations
prepend_sys_path = .
path_separator = os
file_template = %%(year)d_%%(month).2d_%%(day).2d_%%(hour).2d%%(minute).2d-%%(rev)s_%%(slug)s
timezone = UTC

[post_write_hooks]
hooks = ruff_fix, ruff_format
ruff_fix.type = module
ruff_fix.module = ruff
ruff_fix.options = check --fix REVISION_SCRIPT_FILENAME
ruff_format.type = module
ruff_format.module = ruff
ruff_format.options = format REVISION_SCRIPT_FILENAME
```

Alembic's documentation is explicit about what autogenerate sees. It detects added and removed tables and columns, nullability changes, basic index, unique-constraint and foreign-key changes, and type changes. It does not detect table or column renames, which are "detected as a column add/drop pair, which is not at all the same as a name change". Nor does it detect anonymously named constraints, sequences, or standalone PRIMARY KEY and EXCLUDE constraints ([Autogenerate docs](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)). `alembic check` "runs through the same process" without writing files, so it shares every one of these blind spots. **This research's tests made the gaps concrete.** After a new `TaskStatus.BLOCKED` member was added and the CHECK expression changed from `BETWEEN 1 AND 5` to `BETWEEN 1 AND 9`, `alembic check` reported "No new upgrade operations detected". It detected only the `server_default` change.

Name-based CHECK detection exists but is opt-in, and by design "Expression changes are never detected". You enable it with `autogenerate_plugins=["alembic.autogenerate.*", "alembic.ext.checkconstraint_byname"]` ([Detecting CHECK Constraints](https://alembic.sqlalchemy.org/en/latest/autogenerate.html#detecting-check-constraints)).

Autogenerating the first revision for the models above showed a further trap. **The upgrade created the `taskstatus` type implicitly through `create_table`, but the downgrade dropped the tables and left the type behind.** The next `upgrade head` then failed with `DuplicateObject: type "taskstatus" already exists`. Review every generated file for the same handful of problems. Turn drop-and-add pairs into renames, add `postgresql_using=` for type casts, and add a server default or a backfill before any `nullable=False`. Make enum `CREATE TYPE` and `DROP TYPE` explicit in both directions. Confirm that every constraint name is wrapped in `op.f(...)` and never `None`; Alembic 1.20 now warns about the `None` case.

## PostgreSQL enums, locks and concurrent indexes need hand-written DDL

PostgreSQL allows `ALTER TYPE ... ADD VALUE` inside a transaction, but "the new value cannot be used until after the transaction has been committed". It documents no form that removes a value ([ALTER TYPE](https://www.postgresql.org/docs/current/sql-altertype.html)). Alembic's tool for non-transactional steps is `op.get_context().autocommit_block()`, and its docs carry a warning: "the database transaction preceding the block is unconditionally committed" ([Alembic runtime API](https://alembic.sqlalchemy.org/en/latest/api/runtime.html)). **Explicit helper functions, paired with `postgresql.ENUM(..., create_type=False)` on columns, are the approach consistent with the official docs.** `op.execute()` with literal DDL also works in offline `--sql` mode, where `op.get_bind()` is `None` ([Operation reference](https://alembic.sqlalchemy.org/en/latest/ops.html)). Testing corrected a common version of the "replace enum" recipe. **`ALTER COLUMN ... TYPE` fails when the column has a default typed with the old enum**, with `default for column "status" cannot be cast automatically to type task_status`. The helper below therefore drops the default and restores it:

```python
# migrations/helpers/pg_enum.py
"""Explicit PostgreSQL enum DDL for migrations (works online and with --sql)."""

from collections.abc import Sequence

from alembic import op


def _literal(value: str) -> str:
    return "'" + value.replace("'", "''") + "'"


def create_enum(name: str, values: Sequence[str]) -> None:
    op.execute(f'CREATE TYPE "{name}" AS ENUM ({", ".join(map(_literal, values))})')


def drop_enum(name: str) -> None:
    op.execute(f'DROP TYPE IF EXISTS "{name}"')


def add_enum_value(name: str, value: str, *, after: str | None = None) -> None:
    """Commits first; env.py must set transaction_per_migration=True."""
    position = f" AFTER {_literal(after)}" if after is not None else ""
    with op.get_context().autocommit_block():
        op.execute(f'ALTER TYPE "{name}" ADD VALUE IF NOT EXISTS {_literal(value)}{position}')


def replace_enum(
    name: str, values: Sequence[str], columns: Sequence[tuple[str, str, str | None]]
) -> None:
    """Remove or reorder values: rename the old type, create the new one, recast columns.

    Each column is (table, column, server_default value or None); a default typed with
    the old enum cannot be cast, so it is dropped and restored around the ALTER.
    """
    op.execute(f'ALTER TYPE "{name}" RENAME TO "{name}_old"')
    create_enum(name, values)
    for table, column, default in columns:
        alter = f'ALTER TABLE "{table}" ALTER COLUMN "{column}"'
        op.execute(f"{alter} DROP DEFAULT")
        op.execute(f'{alter} TYPE "{name}" USING "{column}"::text::"{name}"')
        if default is not None:
            op.execute(f"{alter} SET DEFAULT {_literal(default)}")
    op.execute(f'DROP TYPE "{name}_old"')
```

The migration below adds a value and backfills it. It also shows two typing and runtime details found in testing. First, **`postgresql.ENUM`'s constructor is unannotated**, so a column built with it is `Column[Unknown]`, which pyright strict rejects. Declaring the variable as `sa.Enum` fixes that. Second, **a frozen `sa.table()` stub must type an enum column as the enum.** When the stub declared `status` as `sa.String`, offline `--sql` rendered fine. Online, psycopg 3 bound the value as `varchar` and PostgreSQL failed with `operator does not exist: task_status = character varying`. The cookbook's guidance applies in full: "Alembic migrations are designed for schema migrations." Keep small, deterministic data fixes in migrations using `table()`/`column()` stubs, never application models, and move large backfills out ([Alembic cookbook](https://alembic.sqlalchemy.org/en/latest/cookbook.html)).

```python
# migrations/versions/2026_10_05_1300-8c41d2e7a9f0_add_blocked_task_status.py
"""add blocked task status

Revision ID: 8c41d2e7a9f0
Revises: 3f2a9c1d7b10
Create Date: 2026-10-05 13:00:00+00:00
"""

from collections.abc import Sequence

import sqlalchemy as sa
from alembic import op
from sqlalchemy.dialects import postgresql

from migrations.helpers.pg_enum import add_enum_value, replace_enum

revision: str = "8c41d2e7a9f0"
down_revision: str | Sequence[str] | None = "3f2a9c1d7b10"
branch_labels: str | Sequence[str] | None = None
depends_on: str | Sequence[str] | None = None

TASK_STATUS_TYPE: sa.Enum = postgresql.ENUM(name="task_status", create_type=False)

# A frozen, migration-local view of the table: never import application models here.
tasks = sa.table(
    "tasks",
    sa.column("priority", sa.Integer),
    sa.column("status", TASK_STATUS_TYPE),
)


def upgrade() -> None:
    """Upgrade schema."""
    add_enum_value("task_status", "blocked", after="done")
    op.execute(
        tasks.update()
        .where(tasks.c.priority == 5, tasks.c.status == "todo")
        .values(status="blocked")
    )


def downgrade() -> None:
    """Downgrade schema."""
    op.execute("UPDATE tasks SET status = 'todo' WHERE status = 'blocked'")
    replace_enum("task_status", ("done", "in_progress", "todo"), [("tasks", "status", "todo")])
```

The `autocommit_block` warning is not theoretical. During testing, the backfill failed after the block had run. **`alembic_version` stayed at the previous revision, but `'blocked'` was already committed to the type.** `IF NOT EXISTS` is what makes the rerun safe, and `transaction_per_migration=True` confines the damage to one revision. Offline output shows the mechanics: `COMMIT;` immediately before `ALTER TYPE "task_status" ADD VALUE IF NOT EXISTS 'blocked' AFTER 'done';`. The upgrade, the downgrade (which rebuilds the type and restores `'todo'::task_status` as the default) and the re-upgrade all ran cleanly afterwards.

The third-party **alembic-postgresql-enum** (1.10.0, February 2026) automates all of this. It hooks autogenerate to create and drop enum types, detect added, removed and reordered values, and rewrite them through `op.sync_enum_values()` ([PyPI alembic-postgresql-enum](https://pypi.org/project/alembic-postgresql-enum/)). It is designed to close the detection gap shown above; this research did not test it. Two things count against it under these constraints. It offers an `add_type_ignore` option because its generated calls are invisible to type checkers, which is friction under pyright strict. And it is not mentioned in Alembic's docs. The other route is to avoid native enums entirely, with `native_enum=False` or `Text` plus a named `CheckConstraint`. Under the CHECK route, adding a value becomes an ordinary transactional constraint swap. You lose the database-level type, and autogenerate still will not notice an edited expression.

**Run migrations as one deliberate deploy step, never on every app start.** Alembic takes no lock on `alembic_version`. Mike Bayer said in 2016 that "Only one process should be running migrations against a single target database at a time", and he declined to add locking to Alembic ([sqlalchemy-alembic mailing list](https://groups.google.com/g/sqlalchemy-alembic/c/I2AAEUdF2dQ)). Some projects serialise startup migrations with PostgreSQL advisory locks ([honcho #1268](https://github.com/plastic-labs/honcho/pull/1268), [opensanctions #5798](https://github.com/opensanctions/opensanctions/pull/5798)). Those locks hang through PgBouncer's transaction pooling ([IBM mcp-context-forge #4051](https://github.com/IBM/mcp-context-forge/issues/4051)), and replicas then serialise on them ([#4783](https://github.com/IBM/mcp-context-forge/issues/4783)). If you must migrate at startup, the helper below is the typed form of that third-party pattern. It is not an Alembic recommendation:

```python
# migrations/lock.py
from collections.abc import Callable

from sqlalchemy import Connection, text

MIGRATION_LOCK_KEY: int = 727_001


def with_migration_lock(connection: Connection, run: Callable[[Connection], None]) -> None:
    """Serialize concurrent migrators (third-party pattern; avoid behind PgBouncer)."""
    connection.execute(text("SELECT pg_advisory_lock(:k)"), {"k": MIGRATION_LOCK_KEY})
    connection.commit()
    try:
        run(connection)
    finally:
        connection.execute(text("SELECT pg_advisory_unlock(:k)"), {"k": MIGRATION_LOCK_KEY})
        connection.commit()
```

**Give migration sessions a short `lock_timeout`.** PostgreSQL defines it as aborting "any statement that waits longer than the specified amount of time while attempting to acquire a lock", and it applies "separately to each lock acquisition attempt". Setting it at or above `statement_timeout` "is rather pointless" ([PostgreSQL client configuration](https://www.postgresql.org/docs/current/runtime-config-client.html)). The `env.py` above uses session-level `SET`s, which survive per-migration commits, whereas `SET LOCAL` would reset at each commit. A few seconds of lock wait plus a retry in the deploy job keeps DDL from queueing behind a long transaction while application traffic piles up behind the DDL.

For zero-downtime changes the cookbook names "online migration" with dual writes. The usual expand-and-contract order adds nullable columns or new tables first, then deploys code that writes both shapes, and then backfills outside the request path. Only after that does it add the constraints, switch reads to the new shape and, in a later revision, drop the old shape.

**Concurrent index builds must run outside a transaction.** SQLAlchemy's dialect docs state that "the PostgreSQL database requires that the statement be invoked outside of a transaction block", so autocommit is required ([Indexes with CONCURRENTLY](https://docs.sqlalchemy.org/en/21/dialects/postgresql.html#indexes-with-concurrently)). In Alembic that means `autocommit_block()`. The model keeps a plain `index=True`, so `alembic check` stayed clean after this migration:

```python
# migrations/versions/2026_10_05_1400-c7d3e9a1b2f4_index_task_titles.py
"""index task titles

Revision ID: c7d3e9a1b2f4
Revises: 8c41d2e7a9f0
Create Date: 2026-10-05 14:00:00+00:00
"""

from collections.abc import Sequence

from alembic import op

revision: str = "c7d3e9a1b2f4"
down_revision: str | Sequence[str] | None = "8c41d2e7a9f0"
branch_labels: str | Sequence[str] | None = None
depends_on: str | Sequence[str] | None = None


def upgrade() -> None:
    """Upgrade schema."""
    with op.get_context().autocommit_block():  # CONCURRENTLY cannot run in a transaction
        op.create_index(op.f("ix_tasks_title"), "tasks", ["title"], postgresql_concurrently=True)


def downgrade() -> None:
    """Downgrade schema."""
    with op.get_context().autocommit_block():
        op.drop_index(op.f("ix_tasks_title"), table_name="tasks", postgresql_concurrently=True)
```

**PostGIS adds one more autogenerate trap.** GeoAlchemy2's `Geometry` and `Geography` types default to `spatial_index=True`. With autogenerate, the generated migration then tries to create indexes "already automatically created during table creation, which will lead to an error" ([GeoAlchemy2 Alembic docs](https://geoalchemy-2.readthedocs.io/en/latest/alembic.html)). The documented fix wires `alembic_helpers.include_object`, `alembic_helpers.writer` (as `process_revision_directives`) and `alembic_helpers.render_item` into `env.py`. An `env.py` that already has a `process_revision_directives`, like the one above, must compose the two rather than replace one with the other. The alternative is `spatial_index=False` plus an explicitly named GiST `Index`, which keeps index names under your naming convention.

GeoAlchemy2 0.20.0 (12 May 2026) lists classifiers only up to Python 3.13 ([PyPI GeoAlchemy2](https://pypi.org/project/GeoAlchemy2/)). Its main branch ships a `py.typed` marker ([GeoAlchemy2 source](https://github.com/geoalchemy/geoalchemy2/tree/main/geoalchemy2)). A model with `location: Mapped[WKBElement] = mapped_column(Geometry("POINT", srid=4326, spatial_index=False))` type-checked cleanly under strict on both SQLAlchemy lines. `Mapped[WKBElement]` is the honest read type. That result applies to the main branch; check the released wheel you install.

## Tests roll back a real database and gate heads, drift and round trips

The documented test recipe is "Joining a Session into an External Transaction". You open a connection, begin a transaction, and bind a `Session` with `join_transaction_mode="create_savepoint"`. The code under test can then call `commit()` freely, and teardown rolls everything back. The docs note that "The above recipe is part of SQLAlchemy's own CI" ([Joining a Session into an External Transaction](https://docs.sqlalchemy.org/en/20/orm/session_transaction.html#joining-a-session-into-an-external-transaction-such-as-for-test-suites)). The default mode, `"conditional_savepoint"`, comes with the advice that "one of the explicit settings be used". With a plain `connection.begin()` it degrades to `rollback_only` ([Session API](https://docs.sqlalchemy.org/en/20/orm/session_api.html#sqlalchemy.orm.Session.params.join_transaction_mode)). Because the parameter is a `Literal`, pyright strict rejects invented modes such as `"conservative_savepoint"`. The mode only matters when the Session is bound to a `Connection`, as below. In 2.1 it is ignored outright whenever the bind is an `Engine` ([2.1 changelog](https://docs.sqlalchemy.org/en/21/changelog/changelog_21.html)).

```python
# tests/conftest.py
from collections.abc import Iterator

import pytest
from alembic import command
from alembic.config import Config
from sqlalchemy import Engine
from sqlalchemy.orm import Session

from app.db.engine import DATABASE_URL, engine


@pytest.fixture(scope="session")
def alembic_config() -> Config:
    config = Config("alembic.ini")
    config.attributes["database_url"] = DATABASE_URL
    return config


@pytest.fixture(scope="session")
def migrated_engine(alembic_config: Config) -> Engine:
    command.upgrade(alembic_config, "head")
    return engine


@pytest.fixture
def db_session(migrated_engine: Engine) -> Iterator[Session]:
    """Each test runs inside one outer transaction that is always rolled back."""
    with migrated_engine.connect() as connection:
        transaction = connection.begin()
        session = Session(
            bind=connection,
            join_transaction_mode="create_savepoint",
            expire_on_commit=False,
        )
        try:
            yield session
        finally:
            session.close()
            transaction.rollback()
```

Migration tests need three gates. **A single head:** `upgrade head` fails when there are several. `alembic merge heads` writes a tuple `down_revision`, and the docs warn that "if you are too freely branching, merging and labeling, things can get pretty crazy" ([Alembic branches](https://alembic.sqlalchemy.org/en/latest/branches.html)). **No drift:** `alembic check` exits non-zero on detected operations, and it only means something against a database already at head. **A clean round trip:** `downgrade()` is officially optional but "probably a good idea" ([Alembic tutorial](https://alembic.sqlalchemy.org/en/latest/tutorial.html)), and the enum-type trap above shows why a round trip belongs in CI even when downgrades are for development only. In production, roll back with a new forward migration rather than a destructive downgrade. `AutogenerateDiffsDetected` is re-exported from `alembic.util`, and `alembic current --check-heads` (added in 1.17.1) checks that a database has every head applied.

```python
# tests/test_migrations.py
import pytest
from alembic import command
from alembic.config import Config
from alembic.script import ScriptDirectory
from alembic.util import AutogenerateDiffsDetected
from sqlalchemy import Engine


def test_single_head(alembic_config: Config) -> None:
    heads = ScriptDirectory.from_config(alembic_config).get_heads()
    assert len(heads) == 1, f"multiple heads; run `alembic merge heads`: {heads}"


def test_models_match_migrations(alembic_config: Config, migrated_engine: Engine) -> None:
    try:
        command.check(alembic_config)
    except AutogenerateDiffsDetected as exc:
        pytest.fail(str(exc))


def test_round_trip(alembic_config: Config, migrated_engine: Engine) -> None:
    command.downgrade(alembic_config, "base")
    command.upgrade(alembic_config, "head")
```

The third-party **pytest-alembic** (0.13.0, 25 September 2026) packages the same checks as `test_single_head_revision`, `test_upgrade`, `test_model_definitions_match_ddl` and `test_up_down_consistency`. It adds an experimental `downgrade_leaves_no_trace` ([PyPI pytest-alembic](https://pypi.org/project/pytest-alembic/)). It is pre-1.0, and its model-match test duplicates `alembic check`, so pick one of the two. Before a release, `alembic upgrade <current>:head --sql` renders the SQL that will actually run. Any migration that calls `op.get_bind()` fails there, which marks it as online-only.

## Where the tools part ways with the docs, and which choices stay open

Most third-party advice agrees with the official sources. The divergences are specific and nameable:

| Topic | Official position | Divergent tool or guide | Resolution |
|---|---|---|---|
| Typing syntax in examples | Python docs prefer `list[...]`, `X \| None`, `collections.abc` | SQLAlchemy's own examples still show `List[...]`, `Optional[...]` ([Basic Relationship Patterns](https://docs.sqlalchemy.org/en/20/orm/basic_relationships.html)) | Modern syntax works identically; all examples here use it |
| Migration template | Python docs: `X \| Y` | Alembic's `generic` and `pyproject` templates use `Union`/`typing.Sequence` | Ship a custom `script.py.mako` |
| Quoted forward references | Python 3.14: annotations are lazy, quotes unnecessary | SQLAlchemy evaluates `Mapped[]` at runtime; Ruff `UP037`/`TC003` push changes that break mapping | Quote cross-module targets; configure `runtime-evaluated-base-classes` with your own base |
| Timestamp defaults | SQLAlchemy shows both client `default=` and `server_default=` | Its mixin example uses client-side `func.now()` | `server_default` for Alembic-managed schemas |
| Enum changes | Alembic: hand-edit; `autocommit_block` | alembic-postgresql-enum automates detection and rebuilds | Explicit helpers, or adopt the plugin knowing it needs type-ignore comments |
| Startup migrations | Maintainer: one migrator at a time | Projects add advisory locks at startup | Separate deploy step; locks only as a fallback, never through PgBouncer transaction pooling |
| Session settings | SQLAlchemy documents a `connect` event recipe | libpq `options` string via `connect_args` | Either works; `options` costs no extra round trip |
| Spatial indexes | GeoAlchemy2 defaults `spatial_index=True` | Autogenerate then emits duplicate index creation | `alembic_helpers` in `env.py`, or `spatial_index=False` plus a named GiST index |
| Row typing | 2.0 docs recommend `.tuples()` / `Row._t` | 2.1 deprecates both | Unpack rows |
| Driver selection | 2.1: psycopg 3 is "preferred" | Projects that relied on bare `postgresql://` broke on upgrade | Always name the driver |

The remaining choices are genuinely open. The official docs support each option, and the trade-off depends on the codebase:

| Choice | Option A | Option B | What decides it |
|---|---|---|---|
| SQLAlchemy line | 2.0.x (legacy, stable behaviour) | 2.1.x (typed rows, psycopg 3 default) | Under pyright strict, 2.1's typed unpacking is a real gain; the cost is the driver and autoflush changes plus deprecation clean-up |
| Mapping style | Plain `DeclarativeBase` classes | `MappedAsDataclass` with `kw_only=True` per class | Whether unchecked constructors are acceptable; typed factory functions are a middle path |
| Implicit loading | `lazy="raise"` on every relationship | `raiseload("*")` per query | Mapping-level raise is stricter; per-query keeps ad-hoc scripts convenient |
| Enum storage | Native PostgreSQL `ENUM` with explicit helpers | `Text` plus named CHECK, or `native_enum=False` | Native types give DB-level typing but cannot drop values; CHECKs migrate transactionally |
| Enum tooling | Hand-written helpers (official primitives) | alembic-postgresql-enum | Detection of value drift versus a third-party dependency with type-checker friction |
| Primary keys | `uuid.uuid7` in Python | `uuidv7()` on PostgreSQL 18 with `monotonic=True` (2.1) | Need for pre-flush IDs and PG version; `uuid4` where creation time must not leak |
| Server-default drift | `compare_server_default=True` | Default `False` | `True` caught real drift with no false positives in testing; enable if `alembic check` gates CI |
| Config file | `alembic.ini` only | `[tool.alembic]` in `pyproject.toml` | Preference; deployment details stay in `alembic.ini` either way |
| Migration tests | Plain Alembic API in pytest | pytest-alembic | Fewer dependencies versus ready-made tests |
| Scripts and crons | Explicit `with SessionLocal() as s:` everywhere | `scoped_session` registry with `remove()` | Explicit passing is the docs' default; the registry is tolerated outside requests |
| Concurrency model | Sync `Session` in `def` routes | `AsyncSession` per task | No official preference; async needs `lazy="raise"`, `expire_on_commit=False` and an async driver |

## Conclusion

Under pyright strict, SQLAlchemy 2.x types almost everything you write with it: attributes, relationships, queries, DML and, from 2.1, unpacked result rows. What it does not type is what happens at runtime. Annotations are evaluated when models are mapped, which is why a linter's "improvement" can break mapping. Constructors are generated dynamically, which is why misspelled keyword arguments pass the checker. Enum values and CHECK expressions live in the database, out of autogenerate's sight. The practical consequence is that **a green pyright run and a green `alembic check` together still do not prove a schema change is correct.** Only running the migrations against a real PostgreSQL, including a down-and-up round trip, does. That one test catches both the leftover enum type and the uncastable enum default found in this research.

The second takeaway is about timing. 2.1.0 shipped less than two weeks before this report and quietly deprecated the typing workarounds the 2.0 docs recommended. New code should be written so it runs under both lines without warnings: name the driver, unpack rows, and quote relationship targets. Then the decision to move to 2.1 becomes a dependency bump plus a test run, not a refactor. Treat the open choices above, especially dataclass mappings and enum storage, as decisions to record explicitly in the project's standards rather than defaults to inherit.
